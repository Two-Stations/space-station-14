# Анализ и Реализация Системы Отзыва Эвакуационного Шаттла

Этот документ описывает решенную проблему с отзывом эвакуационного шаттла и текущую реализацию этой механики. Изначально в коде отсутствовал какой-либо механизм отзыва, что приводило к невозможности повторно вызвать шаттл. Эта проблема была решена, однако анализ выявил более глубокие архитектурные вопросы, часть из которых все еще актуальна.

---

## 1. Обзор систем завершения раунда

Система завершения раунда в Space Station 14 включает несколько механизмов.

### 1.1. Завершение через эвакуацию (Нарративный способ)

Это основной способ завершения раунда, управляемый двумя ключевыми системами:
- **`RoundEndSystem`**: Высокоуровневая система, которая управляет логикой и таймерами для *запроса* эвакуации.
- **`EmergencyShuttleSystem`**: Управляет физическим состоянием и поведением эвакуационного шаттла.

Команда `callevac` взаимодействует с `RoundEndSystem` для запуска этого процесса.

### 1.2. Прямое завершение раунда (Административный способ)

- **Файл**: `Content.Server/GameTicking/Commands/EndRoundCommand.cs`
- **Команда**: `endround`

Эта команда немедленно завершает раунд, вызывая `_gameTicker.EndRound()` без запуска таймеров или вызова шаттла. Это "жесткий" способ, который следует отличать от "мягкого" нарративного завершения через эвакуацию.

## 2. Историческая проблема и её решение

Ранее в игре существовала проблема: после вызова шаттла и его последующего "отзыва" повторный вызов был невозможен до конца раунда. Анализ показал, что причина была не в ошибке, а в **полном отсутствии механики отзыва**.

### 2.1. Устаревший ошибочный сценарий

1.  **Вызов**: Администратор запускал `callevac`. `RoundEndSystem` начинал отсчет.
2.  **Отправка**: `EmergencyShuttleSystem` отправлял шаттл и помечал станцию как "обслуженную", добавляя ее ID в приватный список `_calledStations`.
3.  **Попытка отзыва**: Команда отзыва (например, `recallevac`) отменяла только таймер в `RoundEndSystem`, но никак не влияла на `EmergencyShuttleSystem`.
4.  **Результат**: ID станции оставался в списке `_calledStations`, и все последующие попытки вызова для этой станции игнорировались до перезапуска раунда.

### 2.2. Текущая реализация отзыва (Исправленное поведение)

Эта проблема была полностью решена путем внедрения полноценного механизма отзыва. Теперь процесс выглядит следующим образом:

1.  **Вызов**: Происходит как и раньше. `EmergencyShuttleSystem` по-прежнему добавляет ID станции в `_calledStations`.
2.  **Отзыв**: Команда отзыва `recallevac` вызывает метод `RoundEndSystem.CancelRoundEndCountdown()`.
3.  **Делегирование отзыва**: `CancelRoundEndCountdown` теперь проверяет, был ли уже вызван шаттл (`_shuttle.IsAnyShuttleCalled()`), и если да, то вызывает новый метод `_shuttle.RecallShuttle(station)`.
4.  **Очистка состояния**: Метод `EmergencyShuttleSystem.RecallShuttle()` выполняет ключевую работу:
    - **Удаляет ID станции из списка `_calledStations`**.
    - Сбрасывает флаг `Called` в компоненте `StationEmergencyShuttleComponent`.
    - Отдает команду шаттлу отстыковаться и вернуться на ЦентКом через FTL.
5.  **Результат**: Состояние системы корректно сбрасывается. При следующем вызове `callevac` `EmergencyShuttleSystem` снова сможет обработать запрос, так как ID станции больше не находится в списке `_calledStations`.

## 3. Анализ реализованного кода

Ниже представлены ключевые фрагменты кода, составляющие работающий механизм отзыва.

### 3.1. `RoundEndSystem.CancelRoundEndCountdown()`

Этот метод теперь выступает в роли диспетчера, который решает, отменить ли только таймер или запустить полноценный отзыв.

```csharp
// В Content.Server/RoundEnd/RoundEndSystem.cs

public void CancelRoundEndCountdown(EntityUid? requester = null, bool forceRecall = false, EntityUid? station = null)
{
    if (_gameTicker.RunLevel != GameRunLevel.InRound)
        return;

    // >>> КЛЮЧЕВОЕ ИЗМЕНЕНИЕ <<<
    // Если какой-либо шаттл уже вызван, делегируем команду отзыва
    if (_shuttle.IsAnyShuttleCalled())
    {
        _shuttle.RecallShuttle(station);
    }
    // >>> КОНЕЦ ИЗМЕНЕНИЯ <<<

    if (!forceRecall && CantRecall)
        return;

    if (_countdownTokenSource == null)
        return;

    // Отменяем только изначальный таймер обратного отсчета
    _countdownTokenSource.Cancel();
    _countdownTokenSource = null;

    // ... остальная логика (анонсы, логи) ...
}
```

### 3.2. `EmergencyShuttleSystem.RecallShuttle()`

Это ядро механики отзыва, отвечающее за сброс состояния и возврат шаттла.

```csharp
// В Content.Server/Shuttles/Systems/EmergencyShuttleSystem.cs

public void RecallShuttle(EntityUid? station = null)
{
    // ... логика определения, какие станции отзывать ...

    foreach (var stationUid in stationsToRecall)
    {
        // >>> КЛЮЧЕВОЕ ИЗМЕНЕНИЕ <<<
        // Удаляем станцию из списка, чтобы ее можно было вызвать снова
        _calledStations.Remove(stationUid);

        if (!TryComp<StationEmergencyShuttleComponent>(stationUid, out var stationComp) || !stationComp.Called)
            continue;

        stationComp.Called = false;

        var shuttleEntity = stationComp.EmergencyShuttle;
        // ... проверка компонентов ...

        // Возвращаем шаттл на ЦентКом
        if (TryComp<StationCentcommComponent>(stationUid, out var centcommComp) && centcommComp.MapEntity.HasValue)
        {
            var homeMap = centcommComp.MapEntity.Value;
            var homeCoords = new EntityCoordinates(homeMap, _random.NextVector2(100f));
            _dock.Undock((shuttleEntity.Value, dockComp));
            _shuttle.FTLToCoordinates(shuttleEntity.Value, shuttleComp, homeCoords, Angle.Zero, hyperspaceTime: 0.1f);
        }
    }

    // Обновляем UI консолей
    CleanupEmergencyConsole();
    _commsConsole.UpdateCommsConsoleInterface();
    UpdateAllEmergencyConsoles();
}
```

## 4. Оставшиеся архитектурные задачи и возможности для улучшения

Несмотря на исправление основной проблемы, первоначальный анализ выявил более глубокие архитектурные вопросы, которые все еще актуальны для будущих доработок, особенно для полноценной поддержки нескольких станций.

### 4.1. Проблема: Глобальное состояние мешает независимой эвакуации

Фундаментальная проблема, которая делает невозможной параллельную или независимую эвакуацию с нескольких станций, заключается в том, что логика отсчета времени построена на **глобальном состоянии**, а не на состоянии, привязанном к каждой станции.

-   В `RoundEndSystem` поле `private CancellationTokenSource? _countdownTokenSource` является **единственным** для всех таймеров вызова.
-   В `EmergencyShuttleSystem` переменные, управляющие таймером на консоли, также являются глобальными.

**Последствия:** Как только шаттл вызывается для одной станции, система переходит в "занятое" состояние, и последующие вызовы для других станций либо игнорируются, либо сбрасывают таймер для всех. Эта проблема подтверждается комментарием разработчика в файле `EmergencyShuttleSystem.Console.cs`:
> `// Realistically most of this shit needs moving to a station component so each station has their own emergency shuttle`
> `// and timer and all that jazz...`

**Рекомендация по рефакторингу:** Создать компонент `StationEmergencyStateComponent`, который будет хранить эти переменные (`CountdownTokenSource`, `ConsoleAccumulator` и т.д.) для каждой станции индивидуально. Системы `RoundEndSystem` и `EmergencyShuttleSystem` должны быть переписаны для работы с этим компонентом, а не с глобальными полями.

### 4.2. Отсутствие механизма отмены в `ShuttleSystem`

Реализация отзыва показала, что в низкоуровневой `ShuttleSystem` **отсутствует встроенный API для безопасной отмены FTL-прыжка**, который уже начался. Текущий метод отзыва просто запускает новый FTL-прыжок, что может привести к поведению "сначала прилетел, потом сразу улетел", если шаттл был близко к цели.

**Рекомендация по рефакторингу:** Добавить в `FTLComponent` флаг отмены (например, `bool CancelRequested`). `ShuttleSystem` должен проверять этот флаг и безопасно прерывать текущий прыжок, возвращая шаттл в управляемое состояние. Это создало бы надежный API для использования в других системах.

---
## 5. Итоговые выводы

1.  **Проблема решена:** Баг с невозможностью повторного вызова шаттла после отзыва полностью исправлен. Механизм отзыва реализован и работает в соответствии с ожиданиями для сценария с одной станцией.
2.  **Сохраняется архитектурный долг:** Для поддержки независимой эвакуации с нескольких станций требуется значительный рефакторинг с целью устранения глобального состояния в системах `RoundEndSystem` и `EmergencyShuttleSystem`.

Текущая реализация является стабильной, но дальнейшее развитие функционала шаттлов потребует решения указанных архитектурных задач.

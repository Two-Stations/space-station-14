# Рефакторинг эвакуации: от исправления отзыва к поддержке нескольких станций

Этот документ объединяет исторический анализ проблемы с отзывом эвакуационного шаттла и представляет пошаговый план по рефакторингу системы для полноценной поддержки нескольких независимых станций.

---

## 1. Предыстория: Решение проблемы отзыва шаттла

Прежде чем приступать к рефакторингу для нескольких станций, важно понять контекст предыдущих исправлений. Изначально в игре существовала фундаментальная проблема: после вызова шаттла и его "отзыва" повторный вызов был невозможен.

### 1.1. Историческая проблема и её решение

Анализ показал, что причина была не в ошибке, а в **полном отсутствии механики отзыва**.

**Устаревший ошибочный сценарий:**
1.  **Вызов**: Администратор запускал `callevac`. `RoundEndSystem` начинал отсчет.
2.  **Отправка**: `EmergencyShuttleSystem` отправлял шаттл и помечал станцию как "обслуженную", добавляя ее ID в приватный список `_calledStations`.
3.  **Попытка отзыва**: Команда отзыва (`recallevac`) отменяла только таймер в `RoundEndSystem`, но никак не влияла на `EmergencyShuttleSystem`.
4.  **Результат**: ID станции оставался в списке `_calledStations`, и все последующие попытки вызова для этой станции игнорировались до перезапуска раунда.

**Текущая реализация отзыва (Исправленное поведение):**
Эта проблема была полностью решена путем внедрения полноценного механизма отзыва, где команда `recallevac` теперь корректно делегируется в `EmergencyShuttleSystem`, который выполняет основную работу:
- **Удаляет ID станции из списка `_calledStations`**.
- Сбрасывает флаг `Called` в компоненте `StationEmergencyShuttleComponent`.
- Отдает команду шаттлу отстыковаться и вернуться на ЦентКом через FTL.

В результате состояние системы корректно сбрасывается, и повторный вызов становится возможным.

### 1.2. Оставшиеся архитектурные задачи

Несмотря на исправление основной проблемы, анализ выявил более глубокие архитектурные вопросы, которые напрямую ведут к необходимости текущего рефакторинга.

**Проблема: Глобальное состояние мешает независимой эвакуации**

Фундаментальная проблема, которая делает невозможной параллельную эвакуацию с нескольких станций, заключается в том, что логика отсчета времени построена на **глобальном состоянии**, а не на состоянии, привязанном к каждой станции.

-   В `RoundEndSystem` поле `private CancellationTokenSource? _countdownTokenSource` является **единственным** для всех таймеров вызова.
-   В `EmergencyShuttleSystem` переменные, управляющие таймером на консоли, также являются глобальными.

**Последствия:** Как только шаттл вызывается для одной станции, система переходит в "занятое" состояние, и последующие вызовы для других станций либо игнорируются, либо сбрасывают таймер для всех. Эта проблема подтверждается комментарием разработчика в файле `EmergencyShuttleSystem.Console.cs`:
> `// Realistically most of this shit needs moving to a station component so each station has their own emergency shuttle`
> `// and timer and all that jazz...`

**Вывод:** Хотя баг с отзывом шаттла исправлен, сохранился архитектурный долг, который необходимо устранить для поддержки независимой эвакуации с нескольких станций.

---

## 2. План рефакторинга для поддержки нескольких станций

Этот раздел описывает технический план по устранению архитектурного долга.

### 2.1. Цель

Реализовать возможность независимого вызова, отсчета времени и прибытия эвакуационных шаттлов для каждой станции на сервере.

**Ключевые требования:**
- Команда `callevac` (или ее аналог) должна позволять вызывать шаттл для конкретной станции с уникальным таймером.
- Вызов шаттла для одной станции не должен блокировать или влиять на вызов для другой.
- Каждая станция должна иметь свой собственный, полностью независимый таймер эвакуации.
- Раунд должен завершаться только после того, как **все** вызванные эвакуационные шаттлы **пристыкуются** к конечной точке (ЦентКом).
- Решение должно быть масштабируемым для поддержки двух и более станций.

### 2.2. Текущие ограничения и коренная проблема: Глобальное состояние

Как указано в предыстории, причина кроется в использовании **глобального состояния** — набора полей в системных классах, которые хранят единое состояние для всего сервера.

**Проблемные поля:**

1.  **В `Content.Server/RoundEnd/RoundEndSystem.cs`:**
    - `private CancellationTokenSource? _countdownTokenSource`: Единый токен отмены для таймера вызова.

2.  **В `Content.Server/Shuttles/Systems/EmergencyShuttleSystem.Console.cs`:** Это основной источник проблем.
    - `public bool EmergencyShuttleArrived`: Глобальный флаг прибытия.
    - `public bool EarlyLaunchAuthorized`: Глобальный флаг авторизации раннего старта.
    - `private float _consoleAccumulator`: **Главный глобальный таймер** до старта.
    - `private bool _launchedShuttles`, `public bool ShuttlesLeft`: Глобальные флаги отбытия.
    - `private CancellationTokenSource? _roundEndCancelToken`: Глобальный токен для завершения раунда по таймерu.

Любая попытка вызвать второй шаттл приводит к перезаписи этих глобальных переменных.

### 2.3. Предлагаемое решение: Переход к состоянию на уровне станции

Для решения этой проблемы необходимо перенести все глобальные переменные, связанные с состоянием эвакуации, в новый компонент, который будет существовать на каждой сущности-станции.

**Новый компонент: `StationEmergencyStateComponent`**

**Файл:** `Content.Server/Station/Components/StationEmergencyStateComponent.cs`
```csharp
[RegisterComponent]
public sealed partial class StationEmergencyStateComponent : Component
{
    /// <summary>
    /// Токен отмены для таймера, который запускает вызов шаттла.
    /// </summary>
    [DataField]
    public CancellationTokenSource? CountdownToken;

    /// <summary>
    /// Флаг, что шаттл этой станции прибыл.
    /// </summary>
    [DataField]
    public bool Arrived;

    /// <summary>
    /// Флаг, что для этой станции разрешен ранний запуск.
    /// </summary>
    [DataField]
    public bool EarlyLaunchAuthorized;

    /// <summary>
    /// Основной таймер отсчета до запуска шаттла (в секундах).
    /// </summary>
    [DataField]
    public float ConsoleAccumulator = float.MinValue;
}
```
Этот компонент должен быть добавлен к прототипу каждой станции, у которой есть эвакуационный шаттл.

### 2.4. План реализации (ИСПРАВЛЕННЫЙ)

1.  **Создать `StationEmergencyStateComponent.cs`**.
2.  **Интегрировать компонент** в прототипы станций.
3.  **Рефакторинг `RoundEndSystem`**: Адаптировать для работы с `StationEmergencyStateComponent` конкретной станции.
4.  **Рефакторинг `EmergencyShuttleSystem`**:
    - Удалить глобальные поля.
    - Переписать `UpdateEmergencyConsole` для итерации по станциям.
    - Адаптировать `EarlyLaunch`, `CheckForLaunch` для работы с ID станции.
    - Заменить глобальные анонсы на станционные, где это необходимо.
5.  **Реализация новой логики завершения раунда**:
    - В `EmergencyShuttleSystem` удалить старый `Timer.Spawn`, завершающий раунд.
    - Добавить `HashSet<EntityUid> _arrivedAtCentcommStations`.
    - Создать обработчик для `AfterDockEvent`, который будет заполнять новый `HashSet`.
    - Реализовать функцию `CheckRoundEnd()` и вызывать из нее `_roundEnd.EndRound()`.
6.  **Адаптация команд и UI**:
    - Модифицировать команду `callevac`, чтобы она могла принимать ID станции.
    - **UI**: Изменить `EmergencyConsoleBoundUserInterfaceState`, чтобы он получал состояние из `StationEmergencyStateComponent` той станции, на которой находится консоль.

### 2.5. Анализ зависимостей и рисков (ДОПОЛНЕННЫЙ)

-   **Файлы для изменения**:
    - `Content.Server/RoundEnd/RoundEndSystem.cs`
    - `Content.Server/Shuttles/Systems/EmergencyShuttleSystem.cs` и `EmergencyShuttleSystem.Console.cs` (**очень большие изменения**)
    - `Content.Server/Station/Prototypes/station.yml`
    - `Content.Server/GameTicking/Commands/CallEmergencyShuttleCommand.cs` (`callevac`)
    - `Content.Shared/Shuttles/BUIStates/EmergencyShuttleConsoleState.cs` (UI)

-   **Системы с высоким риском поломки**:
    - **UI консоли эвакуации**: **Самый высокий риск.** Нужно гарантировать, что UI будет корректно получать и отображать таймер для *своей* станции.
    - **Логика завершения раунда**: Новый, событийно-ориентированный механизм сложнее старого. Ошибка в обработчике `AfterDockEvent` (например, неверное определение грида ЦентКома) может привести к тому, что раунд никогда не закончится.
    - **Игровые анонсы**: Необходимо тщательно проконтролировать, чтобы важные сообщения о статусе шаттла доставлялись правильному экипажу и не вводили в заблуждение.

-   **Стратегия митигации рисков**:
    1.  **Поэтапный рефакторинг**: Начинать с создания компонента и переноса одного поля за другим, проверяя работоспособность на каждом шаге.
    2.  **Тестирование UI**: После каждого изменения состояния, от которого зависит UI, тщательно тестировать консоль шаттла в игре.
    3.  **Тестирование логики завершения**: Создать тестовый сценарий с двумя станциями, вызвать оба шаттла, отозвать один, дождаться завершения раунда и убедиться, что все сработало корректно.
    4.  **Обратная совместимость команд**: Команду `callevac` можно сначала оставить без изменений (работающей на "основной" станции), а затем добавить опциональный аргумент для выбора конкретной станции.

# Рефакторинг эвакуации: от исправления отзыва к поддержке нескольких станций

Этот документ объединяет исторический анализ проблемы с отзывом эвакуационного шаттла и представляет пошаговый план по рефакторингу системы для полноценной поддержки нескольких независимых станций.

---

## 1. Предыстория: Решение проблемы отзыва шаттла

Несмотря на ранее внедренную механику отзыва шаттла, анализ выявил, что логика отсчета времени построена на **глобальном состоянии** (глобальные поля в `RoundEndSystem` и `EmergencyShuttleSystem`), что делает невозможной параллельную эвакуацию с нескольких станций.

**Вывод:** Сохранился архитектурный долг, который необходимо устранить для поддержки независимой эвакуации.

---

## 2. План рефакторинга для поддержки нескольких станций

### 2.1. Цель

Реализовать возможность независимого вызова, отсчета времени и прибытия эвакуационных шаттлов для каждой станции на сервере, обеспечив отказоустойчивость и масштабируемость.

### 2.2. Предлагаемое решение: Переход к состоянию на уровне станции

Перенести все глобальные переменные, связанные с состоянием эвакуации, в новый компонент `StationEmergencyStateComponent`, который будет существовать на каждой сущности-станции.

### 2.3. План реализации

1.  **Создание Компонентов Состояния:**
    *   `StationEmergencyStateComponent.cs`: Для хранения **сериализуемого** состояния эвакуации (флаги, таймеры в виде `float` или `TimeSpan`).
    *   `ShuttleStationComponent.cs`: Для установки надежной связи "шаттл -> станция".

2.  **Основной Рефакторинг `EmergencyShuttleSystem` и `RoundEndSystem`**:
    *   Переписать для работы с `StationEmergencyStateComponent` вместо глобальных полей.
    *   **Важно:** Несериализуемые типы, такие как `CancellationTokenSource`, должны храниться во временных словарях (`Dictionary<EntityUid, CancellationTokenSource>`) внутри самих систем, а не в компонентах (см. раздел 4.1).

3.  **Реализация Новой Логики Завершения Раунда:**
    *   Использовать `HashSet`'ы для отслеживания вызванных и прибывших шаттлов.
    *   Подписаться на `AfterDockEvent` (успех) и событие уничтожения шаттла (отказ) для корректного обновления состояния.
    *   Реализовать `CheckRoundEnd()` для проверки условия завершения раунда.

4.  **Реализация Логики Отказа (уничтожение станции):**
    *   Подписаться на событие уничтожения станций и автоматически отзывать соответствующий шаттл.

5.  **Адаптация Зависимых Систем (см. раздел 3, 5 и 6):**
    *   Рефакторинг **Системы целей (Objectives)**.
    *   Рефакторинг **Игровых режимов (Game Rules)**, завязанных на побеге.
    *   Рефакторинг **UI Консоли связи (Communications Console)**.

6.  **Адаптация Команд и UI:**
    *   Модифицировать все команды, управляющие эвакуацией (`callevac`, `recallshuttle`), добавив автодополнение для выбора станции.
    *   Изменить `EmergencyConsoleBoundUserInterfaceState` для работы с состоянием конкретной станции.

### 2.4. Анализ рисков и зависимостей

-   **Высокий риск:** Рефакторинг затронет множество систем. Наибольшему риску поломки подвержены **UI консолей** и **Система целей (Objectives)**, чья логика полностью зависит от удаляемого глобального состояния.
-   **Обязательная адаптация:** Системы, перечисленные в разделах 3 и 6, **должны быть** адаптированы в рамках этой задачи, иначе их функциональность будет полностью нарушена.

## 3. План адаптации: Игровые режимы и Цели

Этот раздел детализирует изменения, необходимые для ключевых зависимых систем.

### 3.1. Система целей (Objectives) и Игровые режимы (Game Rules)

**Текущая проблема:** Условия, такие как `EscapeShuttleCondition`, и игровые режимы (`RevolutionaryRuleSystem`, `SurvivorRuleSystem`) напрямую обращаются к глобальным свойствам `EmergencyShuttleSystem`, чтобы определить, сбежал ли игрок.

**План решения:**
1.  **Переход на Событийную Модель (см. раздел 5):** Вместо синхронной проверки состояния, системы будут реагировать на новые, высокоуровневые события, генерируемые `EmergencyShuttleSystem` (например, `EmergencyShuttleDepartedEvent`).
2.  **Рефакторинг `EscapeShuttleConditionSystem`:** Система будет слушать `EmergencyShuttleDepartedEvent` и проверять наличие нужных игроков среди пассажиров. В компонент `EscapeShuttleConditionComponent` будет добавлено поле `bool Escaped` для фиксации выполнения.
3.  **Рефакторинг Игровых Режимов:**
    *   **`RevolutionaryRuleSystem`**: Будет использовать новый публичный метод `IsAnyShuttleArrived()`.
    *   **`SurvivorRuleSystem`**: Будет использовать новый метод `GetShuttles()`, возвращающий список всех эвакуационных шаттлов.

### 3.2. UI Консоли связи (Communications Console)

**Текущая проблема:** `CommunicationsConsoleSystem` строит свой UI, используя глобальные данные, что не подходит для многостанционной среды.

**План решения (Локальный контекст):**
Рекомендуемый подход — сделать консоль "осведомленной" о своей собственной станции и отображать только ее статус.

1.  **Рефакторинг `CommunicationsConsoleSystem`:** Метод `UpdateCommsConsoleInterface` будет использовать `_stationSystem.GetOwningStation(uid)` для определения ID своей станции.
2.  Затем он будет запрашивать у `RoundEndSystem` и `EmergencyShuttleSystem` статус эвакуации **для этого конкретного ID станции**. Это потребует создания новых публичных методов в этих системах (например, `GetShuttleTimeLeft(stationId)`).
3.  **Состояние UI:** `CommunicationsConsoleInterfaceState` почти не изменится. Он по-прежнему будет хранить состояние одного шаттла, но теперь это будет гарантированно релевантная информация.
4.  **Действия:** Кнопки "Вызвать" и "Отозвать" на консоли будут автоматически отправлять команду с ID своей родной станции.

*(Альтернатива: в будущем можно расширить UI для отображения списка всех станций, но это является новой функцией, а не исправлением).*

## 4. Дополнительные аспекты и стратегия тестирования

Этот раздел охватывает ранее упущенные, но критически важные технические детали.

### 4.1. Критическое упущение: Сохранение и Загрузка Игры

**Проблема:** Первоначальный план предполагал размещение `CancellationTokenSource` в `StationEmergencyStateComponent` с атрибутом `[DataField]`. Это вызвало бы **ошибку при сохранении игры**, так как данный тип не подлежит сериализации.

**Исправленное решение:**
1.  **`StationEmergencyStateComponent`** должен содержать **только** сериализуемые данные.
2.  **`CancellationTokenSource`** и другие несериализуемые объекты должны управляться **внутри систем** (`RoundEndSystem`, `EmergencyShuttleSystem`) во временных словарях, например, `Dictionary<EntityUid, CancellationTokenSource>`.
3.  **Логика загрузки:** При загрузке игры системы должны уметь восстанавливать свое временное состояние, проходясь по компонентам и заново создавая `CancellationTokenSource` для активных таймеров.

### 4.2. Прочие технические аспекты

*   **Динамическое создание станций:** Все рефакторируемые системы должны подписываться на `StationInitializedEvent`, чтобы корректно обрабатывать станции, созданные в середине раунда.
*   **Идентификация шаттлов:** Любая система, которой нужен список всех эвакуационных шаттлов, должна получать его через новый метод `EmergencyShuttleSystem.GetShuttles()`.

### 4.3. Стратегия тестирования

Для проверки надежности реализованных изменений необходимо провести следующие тесты:
-   **Тест на независимость:** Вызвать шаттл для Станции А, затем для Станции Б, и убедиться, что их таймеры работают независимо, а консоль связи на Станции А показывает только свой таймер.
-   **Тесты на отказоустойчивость:** Уничтожить одну из станций после вызова (ее шаттл должен отозваться). Уничтожить один из шаттлов в пути (раунд должен корректно завершиться по прибытии оставшихся).
-   **Тест на логику целей:** Проверить выполнение общих и специфичных для станции целей на побег.
-   **Тест на сохранение/загрузку:** Сохранить и загрузить игру во время пути шаттла, убедившись, что его состояние и таймеры корректно восстановились.

## 5. Финальное архитектурное уточнение: Высокоуровневые события

Для повышения надежности и чистоты архитектуры, `EmergencyShuttleSystem` должна стать единственным источником правды о состоянии эвакуации.

**Архитектурное решение:** `EmergencyShuttleSystem` становится центральным обработчиком низкоуровневых событий (`AfterDockEvent` и др.). После их анализа она создает и рассылает **новые, простые и однозначные высокоуровневые события**, например: `EmergencyShuttleArrivedAtCentComEvent`, `EmergencyShuttleDepartedEvent`. Все остальные системы (цели, игровые режимы) должны будут слушать **только эти новые события**, что кардинально упростит их код и повысит стабильность.

## 6. Руководство по реализации для зависимых систем

Этот раздел предоставляет конкретные инструкции по адаптации затронутых файлов.

### 6.1. Команды администратора (`CallEmergencyShuttleCommand`, `ShuttleCommands`)
*   **Проблема:** Команды `callevac` и `recallshuttle` работают глобально.
*   **План:**
    1.  Обе команды должны быть модифицированы для приема необязательного аргумента — идентификатора станции (имени или `EntityUid`).
    2.  **`callevac`**: Если аргумент станции предоставлен (`callevac "станция А"`), вызов происходит только для этой станции. Если аргумент опущен, команда должна выводить список доступных станций.
    3.  **`recallshuttle`**: Если аргумент станции предоставлен (`recallshuttle "станция А"`), отзыв происходит только для этой станции. Если аргумент опущен, команда должна выводить список шаттлов, которые *уже находятся в процессе эвакуации* и могут быть отозваны.
    4.  Для обеих команд необходимо реализовать автодополнение, предлагающее на выбор доступные станции.

### 6.2. `Content.Server/Objectives/Systems/EscapeShuttleConditionSystem.cs`
*   **Проблема:** Синхронная проверка побега через `_emergencyShuttle.IsTargetEscaping()`.
*   **Необходимые `using`:** `using Content.Server.Shuttles.Events;` (для новых событий).
*   **План:**
    1.  В `EscapeShuttleConditionComponent` добавить: `[DataField] public bool Escaped;`.
    2.  `OnGetProgress` переписать так, чтобы он возвращал `1f` если `comp.Escaped`, иначе `0f`.
    3.  Создать обработчик для нового события `EmergencyShuttleDepartedEvent`.
    4.  **Логика обработчика:** Перебирает пассажиров в `ev.Passengers`. Для тех, у кого есть активная цель побега, устанавливает `Escaped = true` в их компоненте.

### 6.3. `Content.Server/GameTicking/Rules/RevolutionaryRuleSystem.cs`
*   **Проблема:** Использование глобального `_emergencyShuttle.EmergencyShuttleArrived`.
*   **План:**
    1.  Создать в `EmergencyShuttleSystem` публичный метод `public bool IsAnyShuttleArrived()`.
    2.  В `IsGroupDetainedOrDead` заменить проверку `!_emergencyShuttle.EmergencyShuttleArrived` на `!_emergencyShuttle.IsAnyShuttleArrived()`.

### 6.4. `Content.Server/GameTicking/Rules/SurvivorRuleSystem.cs`
*   **Проблема:** Использование `_eShuttle.GetShuttle()` для получения единственного шаттла.
*   **План:**
    1.  Заменить `GetShuttle()` на новый метод `public List<EntityUid> GetShuttles()` в `EmergencyShuttleSystem`.
    2.  В `AppendRoundEndText` получить список всех шаттлов и проверять, находится ли выживший на карте **любого** из них.

### 6.5. `Content.Server/Communications/CommunicationsConsoleSystem.cs`
*   **Проблема:** `UpdateCommsConsoleInterface` использует глобальные данные для UI.
*   **Необходимые `using`:** `using Content.Server.Station.Components;`.
*   **План:**
    1.  В `UpdateCommsConsoleInterface` получить `stationUid` через `_stationSystem.GetOwningStation(uid)`.
    2.  Создать в `RoundEndSystem` новые публичные методы, принимающие `stationUid`, для получения времени до прибытия шаттла конкретной станции.
    3.  Передать эти локальные данные в `CommunicationsConsoleInterfaceState`.

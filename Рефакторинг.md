# План рефакторинга системы эвакуации для поддержки нескольких станций (Скорректированный)

Этот документ описывает технический анализ и пошаговый план по рефакторингу системы эвакуации с целью обеспечения независимой, масштабируемой эвакуации для каждой игровой станции.

---

## 1. Цель

Реализовать возможность независимого вызова, отсчета времени и прибытия эвакуационных шаттлов для каждой станции на сервере.

**Ключевые требования:**
- Команда `callevac` должна позволять вызывать шаттл для конкретной станции с уникальным таймером.
- Вызов шаттла для одной станции не должен влиять на вызов для другой.
- Каждая станция должна иметь свой собственный, полностью независимый таймер эвакуации до отбытия.
- Раунд должен завершаться только после того, как **все** вызванные эвакуационные шаттлы **пристыкуются** к конечной точке (ЦентКом).
- Решение должно быть масштабируемым для поддержки двух и более станций.

---

## 2. Анализ текущей архитектуры и коренная проблема

### 2.1. Что уже реализовано

Анализ кода показал, что часть функциональности для поддержки нескольких станций уже существует:
- **Индивидуальный вызов**: `EmergencyShuttleSystem` уже использует `HashSet<EntityUid> _calledStations` для отслеживания станций, вызвавших эвакуацию. Это предотвращает повторный вызов для одной и той же станции.
- **Спавн нескольких шаттлов**: Система спроектирована так, чтобы создавать отдельный эвакуационный шаттл для каждой станции на общей карте ЦентКома, используя смещение `ShuttleIndex`, чтобы они не появлялись друг на друге.

### 2.2. Коренная проблема: Глобальное состояние запуска и завершения раунда

Несмотря на наличие индивидуального вызова, вся дальнейшая логика — отсчет времени до запуска, сам запуск и последующее завершение раунда — контролируется **глобальным состоянием**. Это делает независимую эвакуацию невозможной.

**Проблемные глобальные поля в `EmergencyShuttleSystem.Console.cs`:**
- `public bool EmergencyShuttleArrived`: Глобальный флаг прибытия шаттла к станции.
- `public bool EarlyLaunchAuthorized`: Глобальный флаг авторизации раннего старта.
- `private float _consoleAccumulator`: **Главный глобальный таймер**, который отсчитывает время до запуска шаттла. При вызове для второй станции он перезаписывается, нарушая таймер первой.
- `private bool _launchedShuttles`, `public bool ShuttlesLeft`: Глобальные флаги отбытия.
- `private CancellationTokenSource? _roundEndCancelToken`: Глобальный токен, который инициирует `_roundEnd.EndRound()` через фиксированное время после отбытия первого шаттла, не дожидаясь остальных.

Разработчики полностью осознавали эту проблему, о чем свидетельствует комментарий в коде:
> `// Realistically most of this shit needs moving to a station component so each station has their own emergency shuttle and timer and all that jazz...`

---

## 3. Предлагаемое решение: Перенос состояния запуска на уровень станции

Для решения этой проблемы необходимо перенести все глобальные переменные, связанные с состоянием **запуска**, в новый компонент, который будет существовать на каждой сущности-станции.

### 3.1. Новый компонент: `StationEmergencyStateComponent`

**Файл:** `Content.Server/Station/Components/StationEmergencyStateComponent.cs`
```csharp
[RegisterComponent, NetworkedComponent]
public sealed partial class StationEmergencyStateComponent : Component
{
    /// <summary>
    /// Флаг, что шаттл этой станции прибыл к доку.
    /// Используется для UI и логики запуска.
    /// </summary>
    [DataField, ViewVariables(VVAccess.ReadWrite)]
    public bool Arrived;

    /// <summary>
    /// Флаг, что для этой станции разрешен ранний запуск.
    /// </summary>
    [DataField, ViewVariables(VVAccess.ReadWrite)]
    public bool EarlyLaunchAuthorized;

    /// <summary>
    /// Основной таймер отсчета до запуска шаттла этой станции (в секундах).
    /// </summary>
    [DataField, ViewVariables(VVAccess.ReadWrite)]
    public float ConsoleAccumulator = float.MinValue;

    /// <summary>
    /// Флаг, что шаттл этой станции уже был запущен и летит к ЦентКому.
    /// </summary>
    [DataField, ViewVariables(VVAccess.ReadWrite)]
    public bool Launched;

    /// <summary>
    /// Флаг, что анонс о скором отправлении был сделан для этой станции.
    /// </summary>
    [DataField]
    public bool ImminentLaunchAnnounced;
}
```

### 3.2. Новая логика завершения раунда

Текущая логика, завершающая раунд по таймеру после отбытия шаттла, **должна быть полностью удалена**. Новая логика будет основана на фактическом прибытии всех шаттлов.
- **Отслеживание состояния**: `EmergencyShuttleSystem` будет использовать два множества: `_calledStations` (уже есть) и новое `_arrivedAtCentcommStations`.
- **Реакция на событие стыковки (`DockEvent`)**: При стыковке эвакуационного шаттла с ЦентКомом, ID его родной станции добавляется в `_arrivedAtCentcommStations`.
- **Проверка условия завершения раунда**: После каждой стыковки система будет проверять, идентичны ли множества `_calledStations` и `_arrivedAtCentcommStations`. Если да, раунд завершается.

## 4. Безопасный план реализации (Expand-Contract)

Этот план минимизирует ошибки компиляции, используя пошаговую миграцию вместо одномоментного удаления.

### Шаг 1: Расширение (Expand)
1.  **Создать `StationEmergencyStateComponent.cs`**: Определить компонент, как указано в разделе 3.1.
2.  **Добавить `using Content.Server.Station.Components;`** в `EmergencyShuttleSystem.cs`.
3.  **Добавить компонент в прототипы**: Внести `StationEmergencyStateComponent` в YAML-файлы карт (`Resources/Prototypes/Maps/`), где уже есть `StationEmergencyShuttleComponent`.
4.  **НЕ удалять** глобальные переменные на этом этапе. Код должен продолжать компилироваться.

### Шаг 2: Миграция (Migrate)
Это итеративный процесс, где каждая функция переключается на использование нового компонента.

1.  **`AnnounceShuttleDock`**: Изменить эту функцию, чтобы при прибытии шаттла она находила `StationEmergencyStateComponent` для нужной станции и записывала в него начальное время `ConsoleAccumulator`.
2.  **`UpdateEmergencyConsole`**: Переписать эту функцию. Вместо работы с глобальным `_consoleAccumulator`, она должна итерировать по всем станциям с `StationEmergencyStateComponent`, и для каждой индивидуально уменьшать ее собственный `ConsoleAccumulator`. Логика запуска шаттла также переносится внутрь этого цикла.
3.  **`UpdateConsoleState`**: Изменить эту функцию, чтобы она отправляла на клиентский UI данные (`EarlyLaunchTime` и др.) из `StationEmergencyStateComponent`, а не из глобальных полей.
4.  **`EarlyLaunch` и связанные функции**: Переработать всю цепочку авторизации (`OnEmagged` → `EarlyLaunch` ← `CheckForLaunch` ← `OnEmergencyAuthorize`), чтобы она была привязана к ID станции. См. п. 7.3.
5.  **`RecallShuttle`**: Изменить эту функцию, чтобы она сбрасывала состояние (`Arrived`, `Launched` и т.д.) в `StationEmergencyStateComponent` для отозванной станции. См. п. 7.2.
6.  **Новая логика завершения раунда**: Реализовать обработчик `OnShuttleDock(DockEvent args)` и функцию `CheckRoundEnd()`. Эта новая логика с самого начала будет использовать только новые множества `_calledStations` и `_arrivedAtCentcommStations`.

### Шаг 3: Сужение (Contract)
1.  **Проверить зависимости**: Убедиться, что ни одна функция больше не читает из старых глобальных переменных (`_consoleAccumulator`, `EmergencyShuttleArrived`, `EarlyLaunchAuthorized` и т.д.).
2.  **Удалить глобальные переменные**: Теперь можно безопасно удалить эти поля из `EmergencyShuttleSystem.Console.cs`.
3.  **Удалить старый таймер завершения раунда**: Окончательно удалить `Timer.Spawn(...)` из старого кода, если он где-то остался.
4.  **Компиляция**: Если на этом этапе возникают ошибки, это означает, что миграция на шаге 2 была неполной. Эти ошибки укажут на пропущенные места.

## 5. Пример итогового поведения

Чтобы проиллюстрировать, как будет работать система после рефакторинга, рассмотрим следующий сценарий:

1.  **Администратор вызывает шаттл для Станции 1:** `callevac --station Station1`
    - `EmergencyShuttleSystem` добавляет `Station1` в `_calledStations`.
    - Система находит `StationEmergencyStateComponent` на сущности `Station1` и инициализирует ее таймер `ConsoleAccumulator` (например, на 180 секунд).
    - Вызывается `DispatchStationAnnouncement` **только для Станции 1** с сообщением о прибытии шаттла.
    - В `Update` начинает тикать таймер для Станции 1.

2.  **Через минуту администратор вызывает шаттл для Станции 2:** `callevac --station Station2`
    - `EmergencyShuttleSystem` добавляет `Station2` в `_calledStations`.
    - Система находит `StationEmergencyStateComponent` на сущности `Station2` и инициализирует ее таймер `ConsoleAccumulator` (например, на 180 секунд).
    - Вызывается `DispatchStationAnnouncement` **только для Станции 2**.
    - В `Update` теперь независимо друг от друга обновляются два таймера: один для Станции 1 (осталось ~120с), другой для Станции 2 (осталось 180с).

3.  **Шаттл Станции 1 отправляется и стыкуется с ЦентКомом.**
    - Срабатывает `DockEvent`.
    - Система определяет, что это эвакуационный шаттл Станции 1, и добавляет `Station1` в `_arrivedAtCentcommStations`.
    - Вызывается `CheckRoundEnd()`. Сравнение множеств показывает, что `_calledStations` (`{Station1, Station2}`) не равен `_arrivedAtCentcommStations` (`{Station1}`). Раунд **не завершается**.

4.  **Шаттл Станции 2 отправляется и стыкуется с ЦентКомом.**
    - Срабатывает `DockEvent`.
    - Система определяет, что это шаттл Станции 2, и добавляет `Station2` в `_arrivedAtCentcommStations`.
    - Вызывается `CheckRoundEnd()`. Теперь `_calledStations` (`{Station1, Station2}`) и `_arrivedAtCentcommStations` (`{Station1, Station2}`) идентичны.
    - Условие выполнено. Система вызывает `_roundEnd.EndRound()`. **Раунд завершается.**

Этот сценарий полностью соответствует поставленной цели и будет реализован в ходе данного рефакторинга.

-   **Системы с высоким риском поломки**:
    - **UI консоли эвакуации**: **Самый высокий риск.** UI тесно связан с таймером. Нужно гарантировать, что он будет корректно получать и отображать таймер для *своей* станции из `StationEmergencyStateComponent`.
    - **Логика завершения раунда**: Новый, событийно-ориентированный механизм сложнее старого. Ошибка в обработчике `DockEvent` может привести к тому, что раунд никогда не закончится.
    - **Зависимые системы**: Системы, использующие `EmergencyShuttleSystem` (например, для проверки условий побега антагонистов), должны быть проверены на совместимость с новой, многостанционной логикой.

-   **Стратегия митигации рисков**:
    1.  **Использовать безопасный план реализации (Expand-Contract)**, описанный в разделе 4.
    2.  **Тестирование UI**: После каждого шага миграции тщательно тестировать консоль шаттла в игре на разных станциях.
    3.  **Тестирование логики завершения**: Создать тестовый сценарий с двумя станциями, вызвать оба шаттла, отозвать один, дождаться завершения раунда и убедиться, что все сработало корректно.

## 7. Практические уроки и подводные камни реализации

Этот раздел документирует неочевидные моменты и ошибки, выявленные в ходе анализа, чтобы помочь реальному разработчику.

### 7.1. Правильное событие стыковки: `DockEvent`
Изначально предполагалось использовать вымышленное событие `AfterDockEvent`. **Это неверно.** Правильное событие, которое рассылается системой `DockingSystem` после успешной стыковки, — это глобальное `DockEvent`.

**Как его использовать:**
- Подписаться на него глобально: `SubscribeLocalEvent<DockEvent>(OnShuttleDock);`
- Обработчик должен иметь сигнатуру `private void OnShuttleDock(DockEvent args)`.
- Внутри обработчика необходимо проверить участников события `args.GridAUid` и `args.GridBUid`. Один из них будет шаттлом (имеет `EmergencyShuttleComponent`), а другой — гридом ЦентКома (имеет `StationCentcommComponent`). Порядок не гарантирован, поэтому требуется проверка в обе стороны.

### 7.2. Гранулярность очистки состояния (`RecallShuttle`)
Критически важно обеспечить, чтобы отзыв шаттла для одной станции не влиял на другие.
- **Проблема:** Неосторожный рефакторинг может привести к тому, что вызов `RecallShuttle(station_A)` сбросит состояние эвакуации для всех станций.
- **Решение:** Функция `CleanupEmergencyConsole` должна быть модифицирована, чтобы принимать опциональный аргумент `EntityUid? stationUid`. Если `stationUid` передан, сбрасывается только компонент `StationEmergencyStateComponent` для этой станции. `RecallShuttle` должен корректно вызывать этот вариант функции.

### 7.3. Цепная реакция в логике авторизации
Рефакторинг логики досрочного запуска — это каскад изменений.
- **Источник изменений:** Метод `EarlyLaunch` должен стать станционно-зависимым и принимать `EntityUid stationUid`.
- **Последствия:** Это немедленно вызовет ошибки компиляции во всех местах, где он вызывался. Потребуется изменить:
    - `CheckForLaunch` → должен принимать `stationUid` и передавать его в `EarlyLaunch`.
    - `OnEmergencyAuthorize` (обработчик нажатия кнопки в консоли) → должен определить, к какой станции относится консоль (`_station.GetOwningStation(uid)`), и передать этот ID в `CheckForLaunch`.
    - `OnEmagged` → также должен определить станцию и передать ее ID в `EarlyLaunch`.
- **Вывод:** При работе с этой логикой всегда нужно отталкиваться от источника события (например, консоли), получать ID станции и передавать его "вверх" по цепочке вызовов.

### 7.4. Внимание к `DeviceNetwork` пакетам для UI
Для обновления таймеров на экранах шаттлов используются пакеты `DeviceNetwork`. При их формировании легко допустить ошибку и использовать глобальные данные вместо станционных.
- **Проблема:** В коде `EarlyLaunch` можно по ошибке использовать старый метод типа `_roundEnd.GetStation()`. Это баг, так как он вернет глобальное значение, а не ту станцию, где был авторизован запуск.
- **Решение:** При создании `payload` для `DeviceNetwork` необходимо явно получать `MapUid` для грида станции, к которой относится шаттл. Данные о станции должны быть получены из контекста (например, из `stationUid`, переданного в `EarlyLaunch`).

### 7.5. Важность `Dirty()` при изменении компонентов
Компонент `StationEmergencyStateComponent` должен быть помечен как `[NetworkedComponent]`, так как его данные (оставшееся время) должны отправляться клиентам для отображения в UI.
- **Проблема:** Если просто изменить поле компонента (`state.ConsoleAccumulator -= frameTime;`), система не узнает, что данные изменились и их нужно синхронизировать.
- **Решение:** После каждого изменения полей компонента `StationEmergencyStateComponent` необходимо вызывать метод `Dirty(uid, component)`. Например: `Dirty(stationUid, stationState);`. Это пометит компонент как "грязный", и его новое состояние будет отправлено клиентам в следующем сетевом тике.

### 7.6. Заметки о прототипах и командах
- **Путь к прототипам станций:** Фактическое определение станций находится не в одном файле `station.yml`, а распределено по файлам карт в `Resources/Prototypes/Maps/`. Именно в них нужно добавлять `StationEmergencyStateComponent`.
- **Команда `callevac`:** Команда уже имеет базовую поддержку `stationUid`, что делает ее хорошей отправной точкой для тестирования.

### 7.7. Необходимые `using` директивы
При создании новых файлов и модификации существующих потребуются новые `using` директивы. Компилятор укажет на их отсутствие. Основные из них:
- **`Content.Server/Station/Components/StationEmergencyStateComponent.cs`**:
    - `using Robust.Shared.GameStates;`
    - `using Robust.Shared.Prototypes;`
    - `using Robust.Shared.ViewVariables;`
- **`Content.Server/Shuttles/Systems/EmergencyShuttleSystem.cs`**:
    - `using Content.Server.Station.Components;`
- **`Content.Server/Shuttles/Systems/DockingSystem.cs`** (для просмотра событий):
    - `using Content.Shared.Shuttles.Events;`

Этот список не исчерпывающий, но покрывает основные моменты, которые могут вызвать ошибки "Class not found".

# Документация по коду Space Station 14 (Детальная)

Это руководство предоставляет детальный технический анализ ключевых систем Space Station 14. Оно предназначено для разработчиков, которым необходимо глубокое понимание кода.

## 1. Начните отсюда: Официальная документация

Прежде чем углубляться в этот технический документ, **настоятельно рекомендуется** изучить **[официальную документацию SS14](https://docs.spacestation14.io/)**. Она дает базовое понимание архитектуры (ECS), процессов создания контента и общие принципы работы, на которые опирается данный анализ.

## 2. Система спавна игроков

Эта система управляет всем процессом от момента, когда игрок готов войти в раунд, до его появления в игровом мире в качестве управляемого персонажа. Процесс является сложным и асинхронным, он построен на событиях и взаимодействии нескольких ключевых систем.

### 2.1. `GameTicker` - Дирижер процесса

Файл: `Content.Server/GameTicking/GameTicker.Spawning.cs`

`GameTicker` инициирует и контролирует общую логику спавна.

### 2.1.1. Обновление информации в лобби

Файл: `Content.Server/GameTicking/GameTicker.cs`

#### Ключевой метод: `UpdateInfoText()`
Этот метод отвечает за сбор актуальной информации о состоянии раунда (выбранная карта, режим игры) и ее отправку всем игрокам в лобби. Любая система, которая изменяет состояние раунда до его начала (например, выбирает карту), должна вызывать этот метод, чтобы игроки увидели изменения в UI.

#### Ключевой метод: `SpawnPlayers(List<ICommonSession> readyPlayers, ...)`
Этот метод вызывается в начале раунда для спавна всех готовых игроков.

**Логика выполнения:**
1.  **`RaiseLocalEvent(new RulePlayerSpawningEvent(...))`**: В самом начале он создает событие `RulePlayerSpawningEvent`. Это дает игровым правилам (например, режиму "Ядерные оперативники" или "Волшебник") возможность первыми обработать спавн и, возможно, "забрать" некоторых игроков для своих нужд, превратив их в антагонистов.
2.  **`_stationJobs.AssignJobs(...)`**: Для оставшихся игроков система `StationJobsSystem` распределяет профессии в соответствии с их предпочтениями и доступными слотами на станциях.
3.  **`_stationJobs.AssignOverflowJobs(...)`**: Игроки, не получившие профессию по предпочтениям, распределяются на оставшиеся свободные места.
4.  **`SpawnPlayer(...)`**: Для каждого игрока, получившего профессию, вызывается одноименный метод `SpawnPlayer`, который выполняет спавн конкретного персонажа.

#### Ключевой метод: `SpawnPlayer(ICommonSession player, ...)`
Этот перегруженный метод выполняет спавн одного игрока, как в начале раунда, так и при позднем подключении (late join).

**Логика выполнения:**
1.  **Проверки**: Метод проверяет, разрешен ли поздний вход, не забанен ли игрок на выбранной профессии и т.д.
2.  **`RaiseLocalEvent(new PlayerBeforeSpawnEvent(...))`**: Перед непосредственным созданием персонажа создается событие `PlayerBeforeSpawnEvent`. Это еще одна точка для перехвата спавна. Например, система выбора антагонистов для позднего подключения может обработать это событие и заспавнить игрока как предателя. Если это событие было обработано (`bev.Handled == true`), стандартная логика спавна прерывается.
3.  **Выбор профессии**: Если профессия не была указана, она выбирается на основе приоритетов игрока (`_stationJobs.PickBestAvailableJobWithPriority`).
4.  **`DoSpawn(...)`**: Вызывается финальный метод, который выполняет основную работу по созданию сущности.
5.  **Анонс**: Если это не "тихий" спавн, `ChatSystem` используется для отправки объявления на станцию о прибытии нового члена экипажа.
6.  **`RaiseLocalEvent(new PlayerSpawnCompleteEvent(...))`**: В самом конце создается событие `PlayerSpawnCompleteEvent`, которое уведомляет другие системы о том, что игрок успешно заспавнился.

### 2.2. `StationSpawningSystem` - Исполнитель спавна

Файл: `Content.Server/Station/Systems/StationSpawningSystem.cs`

Эта система является "руками" `GameTicker`. Она отвечает за фактическое создание сущности персонажа и его оснащение.

#### Ключевой метод: `SpawnPlayerCharacterOnStation(...)`
Это высокоуровневый метод, который просто создает событие `PlayerSpawningEvent` и запускает процесс поиска точки спавна и создания моба.

#### Ключевой метод: `SpawnPlayerMob(...)`
Это "рабочая лошадка" системы. Метод принимает координаты, профиль и профессию и выполняет следующие действия:
1.  **Определение сущности**: На основе профессии (`job.JobEntity`) или расы (`species.Prototype`) определяется, какую сущность нужно создать.
2.  **`Spawn(...)`**: Создается пустая сущность персонажа.
3.  **`_humanoidSystem.LoadProfile(...)`**: На сущность применяются данные из `HumanoidCharacterProfile` (внешность, имя и т.д.).
4.  **`EquipRoleLoadout(...)` и `EquipStartingGear(...)`**: Персонаж получает стартовый набор снаряжения, определенный в его профессии.
5.  **`SetPdaAndIdCardData(...)`**: Настраиваются его КПК и ID-карта: прописываются имя, профессия и выдаются доступы, соответствующие профессии.

#### Ключевое событие: `PlayerSpawningEvent`
Это событие, определяемое в этом же файле, служит связующим звеном. Когда `GameTicker` хочет заспавнить игрока, он не делает это напрямую. Он вызывает `SpawnPlayerCharacterOnStation`, который создает `PlayerSpawningEvent`. Системы, отвечающие за поиск места спавна (например, `SpawnPointSystem`), слушают это событие.

### 2.3. `SpawnPointSystem` - Поиск места

Файл: `Content.Server/Spawners/EntitySystems/SpawnPointSystem.cs`

Эта система отвечает на `PlayerSpawningEvent` и ее единственная задача — найти подходящую точку для спавна, обладая многоуровневой системой поиска для надежности.

#### Ключевой метод: `OnPlayerSpawning(PlayerSpawningEvent args)`
**Логика выполнения:**
1.  **Проверка**: Если в `args.SpawnResult` уже есть сущность (т.е. другой обработчик события уже заспавнил игрока), метод ничего не делает.
2.  **Основной поиск**: Система ищет все сущности с компонентом `SpawnPointComponent` на указанной станции и фильтрует их:
    *   Для **позднего подключения** (`_gameTicker.RunLevel == GameRunLevel.InRound`) выбираются точки с `SpawnType == SpawnPointType.LateJoin`.
    *   Для **старта раунда** (`_gameTicker.RunLevel != GameRunLevel.InRound`) выбираются точки с `SpawnType == SpawnPointType.Job`, соответствующие профессии игрока (`args.Job`). Если у игрока или у точки спавна нет привязки к профессии, они также считаются подходящими.
3.  **Резервный поиск (Fallback 1)**: Если на первом этапе не найдено ни одной подходящей точки, система выполняет второй проход: она ищет **любую** сущность с `SpawnPointComponent` на той же станции, игнорируя тип спавна и профессию.
4.  **Последний резервный поиск (Fallback 2)**: Если и на втором этапе ничего не найдено, система делает последнюю попытку: ищет **любую** точку спавна на **любой** станции в игре.
5.  **Выбор точки**: Из списка, полученного на одном из успешных этапов поиска, выбирается случайная точка.
6.  **Финальный спавн**: Вызывается `_stationSpawning.SpawnPlayerMob(...)` с найденными координатами. Результат (созданная сущность) записывается в `args.SpawnResult`.
7.  **Крайний случай**: Если во всей игре не найдено ни единой точки спавна, система заспавнит игрока в координатах (0,0) на карте по умолчанию, чтобы избежать крэша.

## 3. Карты и Станции

Процесс загрузки карты и превращения ее в функциональную игровую станцию — это многоэтапный процесс, который начинается с конфигурационных файлов и заканчивается созданием и настройкой сущностей в игровом мире.

### 3.1. Конфигурация: `GameMapPrototype`

Все начинается с прототипа карты. Это не сама карта, а ее "паспорт", который описывает ее и содержит ключевые конфигурации для раунда.

Файл-пример: `Resources/Prototypes/Maps/bagel.yml`

```yaml
- type: gameMap
  id: Bagel
  mapName: 'Bagel Station'
  mapPath: /Maps/bagel.yml
  minPlayers: 25
  stations:
    Bagel: # ID конфигурации станции
      stationProto: StandardNanotrasenStation
      components:
        - type: StationNameSetup
          mapNameTemplate: '{0} Багель {1}'
        - type: StationJobs
          availableJobs:
            Captain: [ 1, 1 ]
            # ... и так далее
```

**Ключевые поля:**
*   **`id`**: Уникальный идентификатор прототипа (например, `Bagel`). Используется для выбора карты.
*   **`mapPath`**: Путь к файлу самой карты, который содержит описание всех гридов и сущностей.
*   **`stations`**: Словарь, где каждая запись — это конфигурация для создания полноценной станции из гридов на карте.
    *   **`Bagel`**: Вложенный ID (в данном случае тоже `Bagel`) — это идентификатор, который будет искаться на загруженной карте. У грида на карте должен быть компонент `BecomesStation` с таким же `id`.
    *   **`stationProto`**: Прототип для главной сущности-станции, которая будет создана. Эта сущность будет "владеть" гридами.
    *   **`components`**: Список компонентов, которые будут добавлены к сущности-станции. Именно здесь определяется самое важное:
        *   `StationNameSetup`: Как генерируется имя станции.
        *   `StationJobs`: **Какие профессии доступны на станции и в каком количестве.**

### 3.2. Выбор и загрузка карты

#### `GameMapManager`
Файл: `Content.Server/Maps/GameMapManager.cs`

Эта система отвечает за **выбор** карты для следующего раунда.

**Ключевые методы:**
*   **`Initialize()`**: При старте сервера система читает конфигурацию (`game.map`, `game.map_pool`) и формирует очередь ротации карт.
*   **`AllVotableMaps()`**: Возвращает список карт, доступных для голосования, на основе пула карт (`GameMapPoolPrototype`).
*   **`SelectMapByConfigRules()`**: Основной метод, вызываемый `GameTicker`-ом для определения карты раунда. Он либо выбирает карту из ротации, либо случайную, в зависимости от настроек сервера.
*   **`GetSelectedMap()`**: Возвращает выбранный `GameMapPrototype`.

#### Приоритет выбора карты
Когда `GameTicker` запрашивает карту для загрузки, `GameMapManager` возвращает ее, следуя строгому приоритету:

1.  **Консольная переменная `game.map`**: Если этот CVar установлен (например, командой `forcemap` или в конфиг. файле сервера), его значение имеет абсолютный приоритет. `GameMapManager` хранит это значение в поле `_configSelectedMap` и всегда будет возвращать его, игнорируя все остальные варианты.
2.  **Внутренний выбор**: Если CVar `game.map` **не установлен** (пустая строка), `GameMapManager` вернет карты, установленные в его внутренние переменные (`_selectedMap1`, `_selectedMap2`). Эти переменные устанавливаются голосованием или, в нашем случае, командой `force2map`.
3.  **Правила по умолчанию**: Если и CVar пуст, и внутренний выбор не сделан, `GameMapManager` выберет карту сам, используя ротацию или случайный выбор (`SelectMapByConfigRules`).

**Ключевой вывод**: Чтобы принудительно установить карту (или несколько карт), не используя CVar, необходимо сначала **очистить CVar `game.map`**, установив его в пустую строку. В противном случае выбор будет проигнорирован.

#### `MapLoaderSystem`
Файл: `RobustToolbox/Robust.Shared/EntitySerialization/Systems/MapLoaderSystem.cs` (и его части)

Это низкоуровневая система движка, которая непосредственно **загружает** карту из файла.

**Ключевые методы:**
*   **`TryLoadMap(...)`**: Основной метод, используемый в коде игры. Он принимает путь к файлу карты (`ResPath`).
*   **`TryReadFile(...)`**: Вспомогательный метод, который читает `.yml` файл и парсит его в `MappingDataNode` (представление YAML-данных в памяти).
*   **`TryLoadGeneric(...)`**: (Находится в `MapLoaderSystem.Load.cs`) — это сердце системы. Он использует `EntityDeserializer` для того, чтобы пройти по `MappingDataNode` и создать все сущности: `Map`, `MapGrid`, а также все объекты на гриде, применяя к ним компоненты и их свойства, описанные в файле.

### 3.3. Превращение карты в станцию: `StationSystem`

Файл: `Content.Server/Station/Systems/StationSystem.cs`

Просто загрузить карту недостаточно. `StationSystem` отвечает за то, чтобы "оживить" ее, превратив в игровую локацию.

**Ключевой метод: `OnPostGameMapLoad(PostGameMapLoad ev)`**
Этот метод — точка входа. Он слушает событие `PostGameMapLoad`, которое рассылается `GameTicker`-ом сразу после того, как `MapLoaderSystem` закончил свою работу.

**Логика выполнения:**
1.  **Поиск гридов-кандидатов**: Метод итерирует по всем загруженным гридам (`ev.Grids`) и ищет те, у которых есть компонент `BecomesStationComponent`. Он группирует их по `id` из этого компонента.
    *   Пример из файла карты `bagel.yml`: `... - type: BecomesStation id: Bagel`
2.  **Поиск конфигурации**: Для каждого найденного `id` (например, `Bagel`) система обращается к прототипу карты, который был использован для загрузки (`ev.GameMap`), и ищет в словаре `stations` конфигурацию с таким же ключом.
3.  **Создание станции**: Если конфигурация найдена, вызывается `InitializeNewStation(...)`.
    *   **`EntityManager.SpawnEntity(...)`**: Создается главная сущность-станция на основе `stationProto` из конфигурации.
    *   **Добавление компонентов**: К этой сущности-станции применяются все компоненты из `stationConfig.StationComponentOverrides` — именно так станция получает `StationJobsComponent` со списком профессий и другие важные системы.
    *   **Привязка гридов**: Каждый грид-кандидат "привязывается" к созданной сущности-станции. Ему добавляется `StationMemberComponent`, который указывает на его "владельца".
4.  **Финализация**: В конце рассылается событие `StationInitializedEvent`, которое сигнализирует другим системам, что станция полностью готова к работе.

### 3.4. Инициализация карты: `_map.InitializeMap()`

Простой загрузки карты недостаточно, чтобы она стала полностью функциональной. Финальным и ключевым шагом является вызов метода `_map.InitializeMap(MapId mapId)`.

**Роль метода:**
Этот метод запускает последние этапы "оживления" карты и ее содержимого. Он итерирует по всем сущностям на гридах указанной карты и рассылает событие `MapInitEvent`. Системы, отвечающие за игровую логику, слушают это событие, чтобы завершить свою настройку. Например:
*   `StationSpawningSystem` слушает `MapInitEvent`, чтобы найти все `SpawnPointComponent` и добавить к их родительской станции `StationSpawningComponent`. Без этого компонента станция считается непригодной для спавна.
*   Другие системы могут использовать это событие для кэширования сущностей, активации логики и т.д.

**Ключевой вывод**: Если `InitializeMap` не будет вызван для какой-либо карты, станции на этой карте будут "полумертвыми" — они будут существовать, но многие игровые механики, включая спавн, на них работать не будут.

## 4. `GameTicker.RoundFlow.cs` - Управление потоком раунда

Этот частичный класс (`partial class`) `GameTicker` содержит основную логику, управляющую жизненным циклом раунда: от выбора карты и ее загрузки до старта и перезапуска.

### 4.1. Ключевые зависимости

*   **`IMapManager _map`**: Низкоуровневый менеджер карт из движка. Отвечает за создание, удаление и **инициализацию** карт (`InitializeMap`).
*   **`IGameMapManager _gameMapManager`**: Высокоуровневый менеджер, специфичный для контента игры. Отвечает за **выбор** карты для раунда (из пула, по голосованию, по команде).
*   **`MapLoaderSystem _loader`**: Система, которая непосредственно загружает гриды и сущности из `.yml` файлов карты.

### 4.2. Жизненный цикл раунда

1.  **`UpdateRoundFlow(...)`**: Этот метод вызывается каждый тик. Он проверяет, не пора ли начинать обратный отсчет до старта раунда.
2.  **`LoadMaps()`**: Когда до старта раунда остается мало времени (`RoundPreloadTime`), `UpdateRoundFlow` вызывает `LoadMaps`. Этот метод:
    *   Запраширует у `_gameMapManager` выбранные карты.
    *   Вызывает `LoadGameMap(...)` для каждой, который, в свою очередь, использует `_loader` для загрузки сущностей из файла.
    *   **Важно**: на этом этапе карты только загружены в память, но еще не являются полностью "живыми".
3.  **`StartRound()`**: Когда таймер доходит до нуля, вызывается `StartRound`. Это главный метод, запускающий раунд.
    *   **`_map.InitializeMap(mapId)`**: **Ключевой шаг!** Этот метод вызывается для каждой загруженной карты. Он проходит по всем сущностям на карте и рассылает событие `MapInitEvent`. Это событие "оживляет" карту, позволяя системам (например, `StationSpawningSystem`) найти спавн-поинты и подготовиться к спавну игроков. Без этого вызова станция на карте будет нефункциональна.
    *   **`SpawnPlayers(...)`**: После инициализации всех карт вызывается уже знакомый метод спавна игроков.
    *   **`RunLevel = GameRunLevel.InRound`**: Состояние игры меняется, раунд официально начался.
4.  **`RestartRound()`**: Вызывается по окончанию раунда. Он вызывает `ResettingCleanup()`, который выполняет полную очистку: удаляет всех игроков, сбрасывает системы и, что важно, вызывает `_mapManager.Restart()`, который полностью очищает все карты, готовя сервер к новому циклу.

## 5. Общение: Чат, Радио и TTS

Система общения — это сложный механизм, объединяющий локальный чат, радиосвязь и синтез речи (Text-to-Speech). Эти системы тесно переплетены и передают данные друг другу через события.

### 4.1. `ChatSystem` - Точка входа и диспетчер

Файл: `Content.Server/Chat/Systems/ChatSystem.cs`

Эта система является отправной точкой для почти всех сообщений, отправляемых игроками.

#### Ключевой метод: `TrySendInGameICMessage(...)`
Это "главные ворота" для внутриигровых сообщений. Когда игрок нажимает Enter в чате, вызывается этот метод.

**Логика выполнения:**
1.  **Санитизация и обработка**: Сообщение очищается от лишних пробелов, проверяется на наличие префиксов (например, `;` для радио) и специальных команд эмоций.
2.  **`TryProcessRadioMessage(...)`**: Система проверяет, начинается ли сообщение с префикса радиоканала (например, `;` для общего канала).
    *   **Если да**: Сообщение **не отправляется в локальный чат**. Вместо этого оно перенаправляется в `RadioSystem` для дальнейшей обработки. В `RadioSystem` оно будет отправлено как "шепот" на определенный радиоканал, чтобы избежать создания эха.
    *   **Если нет**: Сообщение обрабатывается как локальное.
3.  **Локальная отправка**: В зависимости от типа сообщения (обычная речь, шепот, эмоция) вызывается соответствующий метод (`SendEntitySpeak`, `SendEntityWhisper`, `SendEntityEmote`).
4.  **`SendEntitySpeak(...)` / `SendEntityWhisper(...)`**:
    *   **Трансформация речи**: Сообщение проходит через `TransformSpeechEvent`, которое позволяет другим системам его изменить (например, добавить акцент или заикание).
    *   **Определение получателей**: Метод `GetRecipients` находит всех игроков в пределах слышимости (`VoiceRange` или `WhisperMuffledRange`).
    *   **Отправка клиентам**: `IChatManager` отправляет отформатированное сообщение каждому клиенту-получателю.
    *   **`RaiseLocalEvent(new EntitySpokeEvent(...))`**: **Это ключевой момент.** После отправки сообщения в чат система создает событие `EntitySpokeEvent`. Это событие служит "крючком" для других систем (включая TTS и радио), которые хотят отреагировать на факт речи.

### 4.2. `RadioSystem` - Связь на расстоянии

Файл: `Content.Server/Radio/EntitySystems/RadioSystem.cs`

Эта система отвечает за передачу сообщений на большие расстояния через определенные каналы.

#### Ключевой метод: `SendRadioMessage(...)`
Этот метод вызывается, когда `ChatSystem` обнаруживает радио-префикс.

**Логика выполнения:**
1.  **Поиск передатчика**: Процесс начинается, когда `EntitySpokeEvent` обрабатывается у сущности с `IntrinsicRadioTransmitterComponent`. Система слушает "шепот" на специальном радиоканале.
2.  **Проверка серверов**: Для каналов, не являющихся "дальнего действия" (`longRange: false`), система проверяет наличие активного `TelecomServerComponent` на той же карте. Если сервера нет, сообщение не будет отправлено.
3.  **Поиск приемников**: Система ищет все сущности с `ActiveRadioComponent` (например, надетые гарнитуры), которые подписаны на нужный канал.
4.  **Проверка глушения**: Перед отправкой каждому приемнику система создает `RadioReceiveAttemptEvent`. Это позволяет `JammerSystem` (системе глушения) перехватить и отменить отправку, если частота канала заблокирована.
5.  **Доставка сообщения**: Если все проверки пройдены, на сущности-приемнике создается событие `RadioReceiveEvent`.
6.  **`OnIntrinsicReceive(...)`**: Если у приемника есть `IntrinsicRadioReceiverComponent` и к нему подключен игрок, этот метод получает `RadioReceiveEvent` и отправляет финальное, отформатированное сообщение напрямую клиенту игрока.

### 4.3. `TTSSystem` - Синтез речи (Особенность форка Corvax)

Файл: `Content.Server/Corvax/TTS/TTSSystem.cs`

Эта система "слушает" речь и превращает ее в звук.

#### Ключевой метод: `OnEntitySpoke(EntityUid uid, TTSComponent component, EntitySpokeEvent args)`
Это основной метод, который связывает TTS с остальной системой чата.

**Логика выполнения:**
1.  **Перехват события**: Система слушает `EntitySpokeEvent`, которое, как мы помним, создается `ChatSystem` **после** того, как сообщение было обработано и отправлено в чат.
2.  **Проверка**: Система проверяет, включен ли TTS, есть ли у говорящего `TTSComponent` и не слишком ли длинное сообщение.
3.  **Разделение на "Say" и "Whisper"**:
    *   `args.ObfuscatedMessage != null`: `ChatSystem` заполняет это поле только для шепота. `TTSSystem` использует это, чтобы понять, что нужно генерировать звук для шепота.
    *   Если `ObfuscatedMessage` есть, вызывается `HandleWhisper`.
    *   Если его нет, вызывается `HandleSay`.
4.  **`HandleSay(...)`**:
    *   `GenerateTTS(...)` вызывается для получения аудиоданных из `TTSManager` (который кэширует и делает веб-запросы).
    *   `RaiseNetworkEvent(new PlayTTSEvent(...))`: Создается сетевое событие `PlayTTSEvent` с аудиоданными, которое отправляется всем игрокам в зоне видимости (PVS) говорящего. Клиентская часть системы ловит это событие и воспроизводит звук.
5.  **`HandleWhisper(...)`**:
    *   Генерируются **два** аудиофайла: для полного сообщения и для "заглушенного".
    *   Система вручную перебирает игроков в PVS, измеряет дистанцию и отправляет либо полное аудио (если игрок в `WhisperClearRange`), либо заглушенное, эмулируя эффект "неразборчивого шепота" на расстоянии.

## 5. Прочее: Сектора и Радиочастоты

В этом разделе рассматриваются оставшиеся темы из первоначального запроса, с детальным анализом их реализации в коде.

### 5.1. Радиочастоты и система глушения

Как было упомянуто в разделе про общение, частоты (`frequency`) являются ключевым свойством радиоканалов. Основная система, которая их использует — это `JammerSystem`.

Файл: `Content.Server/Radio/EntitySystems/JammerSystem.cs`

Эта система позволяет создавать в игре устройства-глушилки, которые блокируют радиосвязь на определенных частотах.

#### Ключевой метод: `OnRadioSendAttempt(ref RadioSendAttemptEvent args)`
Это точка входа для механики глушения.
1.  **Перехват события**: `RadioSystem` перед отправкой сообщения в радиоэфир создает событие `RadioSendAttemptEvent`. `JammerSystem` подписывается на это событие.
2.  **Проверка**: Внутри обработчика вызывается метод `ShouldCancelSend`, который и решает, будет ли сообщение заглушено.
3.  **Отмена отправки**: Если `ShouldCancelSend` возвращает `true`, то `JammerSystem` устанавливает `args.Cancelled = true`. `RadioSystem`, видя это, прекращает дальнейшую обработку и не отправляет сообщение.

#### Ключевой метод: `ShouldCancelSend(EntityUid sourceUid, int frequency)`
Это ядро логики глушения.
1.  **Итерация по глушилкам**: Метод ищет все активные сущности с компонентом `ActiveRadioJammerComponent`.
2.  **Проверка диапазона**: Для каждой глушилки проверяется, находится ли источник сообщения (`sourceUid`) в ее радиусе действия (`_transform.InRange(...)`).
3.  **Проверка частоты**:
    *   Если сообщение находится в радиусе действия глушилки, система проверяет поле `FrequenciesExcluded` в `RadioJammerComponent`.
    *   Это поле работает как "белый список". Если частота сообщения (`frequency`) **содержится** в этом списке, глушилка ее **игнорирует**.
    *   Если же `FrequenciesExcluded` равно `null` или не содержит частоту сообщения, то считается, что глушилка нацелена на эту частоту.
4.  **Результат**: Если найдена хотя бы одна глушилка, в радиусе действия которой находится источник, и которая не игнорирует данную частоту, метод возвращает `true` (сообщение будет заглушено). В противном случае — `false`.

### 5.2. "Сектора": Повествовательный элемент и UI-термин

При глубоком анализе кода выяснилось, что в игре **нет единой игровой механики "Сектор"**, связанной с картами, доступом или логикой игры. Этот термин имеет два основных применения, не связанных друг с другом.

#### 1. Повествовательный элемент
В большинстве случаев "сектор" — это просто слово, используемое в текстах для создания атмосферы (`flavor text`). Оно встречается в названиях и описаниях предметов, в целях для антагонистов, в консольных сообщениях и т.д. (например, "обнаружен корабль в секторе 5"). Это не более чем часть повествования, и за этим словом не стоит никакой конкретной системы.

#### 2. Термин в UI (Пользовательский интерфейс)
Единственное место, где "сектор" является техническим термином — это код радиальных меню.

Файл: `Content.Client/UserInterface/Controls/RadialMenu.cs`

В этом файле "сектор" обозначает **геометрический сектор круга**, то есть "кусочек пирога" в радиальном меню.
*   **Интерфейс `IRadialMenuItemWithSector`**: Определяет, что у элемента радиального меню есть свойства `AngleSectorFrom` и `AngleSectorTo` (начальный и конечный угол).
*   **Класс `RadialMenuButtonWithSector`**: Реализует этот интерфейс. Он использует эти углы для отрисовки кнопки в виде сектора круга и для определения, попал ли курсор мыши в область этой кнопки.

**Вывод**: Этот термин в коде UI не имеет никакого отношения к картам, станциям или игровой логике, и является исключительно частью системы отрисовки пользовательского интерфейса.

## 6. Команды и CVar-ы (Консольные переменные)

Эта секция описывает, как создавать консольные команды для администраторов и игроков, и как использовать консольные переменные (CVars) для гибкой настройки поведения игры без изменения кода.

### 6.1. Консольные команды

Консольные команды позволяют выполнять действия в игре через консоль (F7). Они являются основным инструментом для администрирования, отладки и иногда для игровых механик (например, команда `suicide`).

#### Как создать команду
Создание команды — это простой процесс, реализованный в движке RobustToolbox.

1.  **Создайте новый класс**: Команда — это обычный C# класс.
2.  **Унаследуйте `IConsoleCommand`**: Класс должен реализовывать интерфейс `Robust.Shared.Console.IConsoleCommand`.
3.  **Реализуйте интерфейс**:
    *   `string Command { get; }`: Строка, которую нужно ввести в консоли для вызова команды (например, "godmode").
    *   `string Description { get; }`: Краткое описание, которое видит пользователь.
    *   `string Help { get; }`: Подробная справка, обычно с примерами использования.
    *   `void Execute(IConsoleShell shell, string argStr, string[] args)`: Основной метод, содержащий всю логику команды.
        *   `shell`: Консоль, в которую можно писать ответы (`shell.WriteLine(...)`) или ошибки (`shell.WriteError(...)`).
        *   `argStr`: Строка со всеми аргументами.
        *   `args`: Массив аргументов, разделенных по пробелам.
4.  **Используйте зависимости**: Внутри класса команды можно использовать `[Dependency]` для внедрения любых систем и менеджеров (`IEntityManager`, `IPlayerManager` и т.д.), точно так же, как в `EntitySystem`.

Движок автоматически обнаружит ваш новый класс и зарегистрирует команду при запуске.

#### Пример: Упрощенная команда `GodMode`
Файл-источник: `Content.Server/Damage/Commands/GodModeCommand.cs`

```csharp
// using ...

public sealed class GodModeCommand : IConsoleCommand
{
    // Внедряем зависимости, чтобы работать с сущностями и игроками
    [Dependency] private readonly IEntityManager _entManager = default!;
    [Dependency] private readonly IPlayerManager _playerManager = default!;

    public string Command => "godmode";
    public string Description => "Makes you invulnerable to all damage.";
    public string Help => "godmode";

    public void Execute(IConsoleShell shell, string argStr, string[] args)
    {
        // Получаем сущность, к которой привязан игрок, вызвавший команду
        var player = shell.Player as ICommonPlayer;
        if (player?.AttachedEntity is not { } playerEntity)
        {
            shell.WriteError("You don't have an entity!");
            return;
        }

        // Пытаемся получить компонент, если его нет - добавляем. Если есть - удаляем.
        if (_entManager.HasComponent<GodmodeComponent>(playerEntity))
        {
            _entManager.RemoveComponent<GodmodeComponent>(playerEntity);
            shell.WriteLine("Godmode disabled.");
        }
        else
        {
            _entManager.AddComponent<GodmodeComponent>(playerEntity);
            shell.WriteLine("Godmode enabled.");
        }
    }
}
```

### 6.1.1. Автодополнение в командах

Помимо `Execute`, интерфейс `IConsoleCommand` содержит необязательный метод `GetCompletion`, который позволяет реализовать контекстные подсказки (автодополнение) для команды.

**Ключевой метод: `GetCompletion(IConsoleShell shell, string[] args)`**
Этот метод вызывается консолью каждый раз, когда пользователь вводит команду.
*   **`args`**: Массив уже введенных аргументов. Анализируя `args.Length`, можно понять, для какого по счету аргумента нужно предоставить подсказку.
*   **Возвращаемое значение**: Метод должен вернуть объект `CompletionResult`. Чаще всего используется статический метод `CompletionResult.FromHintOptions`, который принимает список строк-подсказок.

**Пример для команды `force2map`**:
```csharp
public CompletionResult GetCompletion(IConsoleShell shell, string[] args)
{
    // Получаем список всех карт
    var maps = _gameMapManager.AllMaps().Select(p => p.ID).ToList();

    // Если пользователь вводит первый аргумент
    if (args.Length == 1)
    {
        return CompletionResult.FromHintOptions(maps, "<map1>");
    }

    // Если пользователь вводит второй аргумент
    if (args.Length == 2)
    {
        // Для удобства можно исключить уже выбранную карту из подсказок
        maps.Remove(args[0]);
        return CompletionResult.FromHintOptions(maps, "<map2>");
    }

    return CompletionResult.Empty;
}
```

### 6.2. CVar-ы (Консольные переменные)

CVar-ы (от "Console Variables") — это мощный инструмент для настройки игры "на лету". Это переменные, значения которых можно менять через консоль или конфигурационные файлы сервера, не перезапуская его. Они используются для всего: от включения/выключения игровых режимов до настройки физики.

#### Как определить CVar
Все CVar-ы для игрового контента определены в одном статическом частичном классе (`partial class`): `Content.Shared.CCVar.CCVars`. Он разбит на множество файлов для удобства.

Файл-пример: `Content.Shared/CCVar/CCVars.Chat.cs`
```csharp
// using ...

public sealed partial class CCVars
{
    // Определяем CVar:
    // 1. Имя в конфиг. файлах ("looc.enabled")
    // 2. Значение по умолчанию (true)
    // 3. Флаги (REPLICATED - значение синхронизируется с клиентом, SERVER - изменять может только сервер)
    public static readonly CVarDef<bool> LoocEnabled =
        CVarDef.Create("looc.enabled", true, CVar.REPLICATED | CVar.SERVER);
}
```

#### Как использовать CVar
Для работы с CVar-ами используется менеджер конфигурации `IConfigurationManager`, который внедряется через `[Dependency]`.

**1. Получение значения:**
Это самый простой способ. Вы просто запрашиваете текущее значение CVar-а.

```csharp
// Внедряем зависимость
[Dependency] private readonly IConfigurationManager _cfg = default!;

// ... в каком-либо методе
var limit = _cfg.GetCVar(CCVars.FlavorLimit);
// ... используем значение
```

**2. Подписка на изменения:**
Часто системам нужно не просто знать текущее значение, а немедленно реагировать на его изменение. Для этого используется подписка.

Файл-источник: `Content.Shared/Throwing/ThrowingSystem.cs`
```csharp
// ...
public sealed class ThrowingSystem : EntitySystem
{
    [Dependency] private readonly IConfigurationManager _configManager = default!;
    private float _frictionModifier;

    public override void Initialize()
    {
        base.Initialize();

        // Подписываемся на изменение CVar-а TileFrictionModifier
        // 1. Менеджер, 2. CVar, 3. Лямбда-функция, которая выполнится при изменении, 4. true - выполнить лямбду сразу же
        Subs.CVar(_configManager, CCVars.TileFrictionModifier, value => _frictionModifier = value, true);
    }
}
```
Этот паттерн очень удобен, так как позволяет кэшировать значение CVar-а в поле системы и автоматически обновлять его, когда администратор меняет настройку.

## 7. Дополнение: Обнаруженные системы в ходе реализации

В процессе работы над системой двух станций были изучены дополнительные системы, не описанные в основной документации.

### 7.1. Система голосования: `VoteManager`

Файл: `Content.Server/Voting/Managers/VoteManager.DefaultVotes.cs`

Эта система управляет всеми стандартными голосованиями в игре: за рестарт, смену игрового режима и выбор карты. Она не является частью `GameTicker`, а работает параллельно, влияя на его настройки.

**Ключевой метод: `CreateMapVote(ICommonSession? initiator)`**
Этот метод отвечает за создание голосования за карту.

**Логика выполнения:**
1.  **`_gameMapManager.CurrentlyEligibleMaps()`**: Получает список всех карт, доступных для голосования.
2.  **`CreateVote(options)`**: Создается стандартное голосование с одним победителем. Для этого используется `VotingSystem`, который управляет логикой сбора голосов и определения победителя.
3.  **`vote.OnFinished`**: После завершения голосования срабатывает это событие. В его обработчике результат голосования (выбранная карта) передается в `_gameMapManager.SelectMap(...)`, что и определяет карту для следующего раунда.

Эта система изначально рассчитана на выбор только одного победителя, что потребовало доработки для поддержки двух станций.

### 7.2. Распределение профессий: `StationJobsSystem.Roundstart.cs`

Файл: `Content.Server/Station/Systems/StationJobsSystem.Roundstart.cs`

Логика распределения игроков по профессиям в начале раунда вынесена в отдельную часть `partial class StationJobsSystem`.

**Ключевой метод: `AssignJobs(...)`**
Этот метод оказался гораздо более гибким, чем предполагалось. Он **уже** поддерживает распределение игроков по нескольким станциям.

**Логика выполнения:**
1.  **Входные данные**: Метод принимает словарь профилей игроков и **список `EntityUid` станций**.
2.  **Сбор доступных профессий**: Система создает словарь `stationJobs`, где для каждой станции из списка хранится количество доступных слотов для каждой профессии.
3.  **Пропорциональное распределение "долей"**: Самая важная часть. Система вычисляет, какую "долю" игроков должна получить каждая станция. Это делается пропорционально количеству свободных мест для профессий определенного "веса" (приоритета). Например, если на одной станции 10 слотов, а на другой 20, то вторая станция получит в два раза больше игроков на этом этапе распределения.
4.  **Случайное назначение**: В рамках выделенной "доли" игроки, выбравшие одинаковые профессии с одинаковым приоритетом, назначаются на случайные из доступных для них должностей на данной станции.

Это открытие позволило не переписывать сложный алгоритм, а просто корректно вызвать его из `GameTicker.Spawning.cs`, передав ему список всех доступных для спавна станций.

## 8. Системы шаттлов: Общая архитектура

В ходе анализа было выявлено, что различные системы шаттлов (эвакуационный, карго, и т.д.) часто следуют общему паттерну проектирования.

1.  **Компонент-маркер на станции**: На главную сущность-станцию добавляется специальный компонент (например, `StationEmergencyShuttleComponent`, `StationCargoShuttleComponent`). Этот компонент служит "сигналом" для соответствующей системы, что данная станция должна иметь свой шаттл. Он также может содержать специфичные для станции настройки (например, путь к файлу карты шаттла).
2.  **Событие `StationPostInitEvent`**: Это событие рассылается системой `StationSystem` после полной инициализации сущности-станции.
3.  **Система-обработчик**: Специализированная система (например, `EmergencyShuttleSystem`) подписывается на `StationPostInitEvent` **только для сущностей, у которых есть ее компонент-маркер**.
4.  **Логика инициализации**: Когда обработчик срабатывает, он выполняет логику по созданию и настройке шаттла специально для этой станции. Это может включать загрузку новой карты (`.yml`), создание сущности шаттла и ее привязку к станции.

Этот модульный подход позволяет гибко наделять станции различными возможностями, просто добавляя к их прототипу нужные компоненты. Проблема в многостанционной среде возникает тогда, когда эти компоненты не добавляются ко всем станциям, или когда система-обработчик содержит ошибочную логику, рассчитанную на единственную станцию (например, использует глобальные переменные или ищет первую попавшуюся сущность вместо той, что привязана к станции).

### 8.1. Эвакуационный шаттл (Архитектура с общим Центкомом)

Дальнейший анализ и новые требования уточнили, что система эвакуации должна использовать **единый Центком** для всех станций. Изначальная логика `EmergencyShuttleSystem` это поддерживает:

1.  **Создание Центкома**: При инициализации первой станции с `StationCentcommComponent` создается уникальная карта Центкома.
2.  **Привязка других станций**: Все последующие станции с этим компонентом обнаруживают уже существующий Центком и просто привязываются к нему, не создавая новых карт.
3.  **Спавн шаттлов**: Для каждой станции на этой **общей карте Центкома** спавнится свой эвакуационный шаттл. Чтобы они не появлялись друг на друге, используется смещение (`ShuttleIndex`).

Проблема заключалась не в спавне, а в **вызове**. Система использовала глобальный флаг `EmergencyShuttleArrived`, из-за которого после вызова шаттла для одной станции, вызовы для всех остальных игнорировались.

**Решение**: Вместо глобального флага `bool` был внедрен `HashSet<EntityUid> _calledStations`, который хранит ID всех станций, уже вызвавших шаттл. Кроме того, в `StationEmergencyShuttleComponent` было добавлено поле `bool Called`, которое отслеживает вызов на уровне компонента. Логика `DockEmergencyShuttle` была изменена, чтобы проверять этот флаг для каждой станции индивидуально, позволяя вызвать шаттлы для всех.

### 8.2. Карго-система и шаттлы (Повышение надежности спавна)

Изначальная логика спавна физического карго-шаттла в `ShuttleSystem.GridFill.cs` оказалась ненадежной. Она использовала метод `TryFTLProximity`, который пытался найти случайное свободное место у станции и часто завершался неудачей, из-за чего шаттл не спавнился вовсе.

**Решение**: Метод `CargoSpawn` был переписан. Вместо рискованного `TryFTLProximity`, он теперь определяет габариты (AABB) станции и создает шаттл на той же карте, но на большом, безопасном и фиксированном расстоянии от станции. Это гарантирует, что шаттл будет создан в 100% случаев.

## 9. Взаимодействие и физика: Buckle, Standing и Piloting

В ходе анализа крэша была изучена цепочка взаимодействий, приводящая к изменению физического состояния игрока.

1.  **`StrapComponent`**: Компонент, который позволяет "пристегивать" другие сущности (например, кресло или консоль пилота).
2.  **`BuckleSystem`**: При взаимодействии с сущностью со `StrapComponent` эта система "пристегивает" игрока. В случае с консолью пилота, она также вызывает `_standing.Down()`, чтобы перевести персонажа в лежачее положение.
3.  **`StandingStateSystem`**: Метод `Down()` меняет визуальное состояние и коллизию, но, вопреки первоначальной гипотезе, **не меняет** `BodyType` напрямую.
4.  **`ShuttleConsoleSystem`**: При начале пилотирования (`AddPilot`) система должна обеспечивать консистентность физического состояния. Именно отсутствие `BlockMovementComponent` при измененном на `Kinematic` `BodyType` (причина изменения которого осталась скрытой в недрах движка, но происходит в результате отсоединения управления от тела).

## 10. EUI: Расширенные Пользовательские Интерфейсы (Анализ по коду)

EUI (Extended User Interfaces) — это система для создания сложных, интерактивных окон, состояние которых полностью управляется сервером. Это обеспечивает синхронизацию данных между клиентом и сервером в реальном времени.

Анализ кода на примере **`CrewManifestEui`** (Манифест экипажа) показывает следующую архитектуру и жизненный цикл.

### 10.1. Ключевые компоненты архитектуры

Система разделена на четыре логических компонента, распределенных по проектам `Content.Server`, `Content.Client` и `Content.Shared`.

1.  **Серверная Система** (`...System.cs`)
    *   **Роль**: Хранит основную логику и данные. Решает, **когда** открыть EUI и **когда** данные для него изменились.
    *   **Пример**: `Content.Server/CrewManifest/CrewManifestSystem.cs`.

2.  **Серверный EUI** (`...Eui.cs` на сервере)
    *   **Роль**: "Поставщик данных". Его главная задача — отвечать на запрос "каково твое текущее состояние?", упаковывая данные в объект `State`.
    *   **Пример**: `Content.Server/CrewManifest/CrewManifestEui.cs`.

3.  **Общее Состояние и Сообщения** (`...State.cs`, `...Messages.cs`)
    *   **Роль**: Простые структуры данных для пересылки по сети. Должны быть помечены атрибутами `[Serializable, NetSerializable]`.
    *   **Пример**: `Content.Shared/CrewManifest/SharedCrewManifestSystem.cs` (в этом файле определены `CrewManifestEuiState` и `RequestCrewManifestMessage`).

4.  **Клиентский EUI и Окно UI**
    *   **Клиентский EUI** (`...Eui.cs` на клиенте): "Получатель данных". Принимает `State` от сервера и передает его в реальное окно для отрисовки.
    *   **Окно UI** (`...Window.cs` или `...Ui.cs`): Отвечает только за отображение. Не содержит сетевой логики.
    *   **Пример**: `Content.Client/CrewManifest/CrewManifestEui.cs` и его окно `CrewManifestUi`.

### 10.2. Жизненный цикл EUI на примере `CrewManifestEui`

#### Шаг 1: Инициация (Открытие окна)

Процесс начинается, когда серверная система решает открыть EUI для игрока.

Файл: `Content.Server/CrewManifest/CrewManifestSystem.cs`
```csharp
public void OpenEui(EntityUid station, ICommonSession session, EntityUid? owner = null)
{
    // 1. Создается серверный объект EUI
    var eui = new CrewManifestEui(station, owner, this);

    // 2. EuiManager получает команду открыть этот EUI для конкретного игрока
    _euiManager.OpenEui(eui, session);

    // 3. Устанавливается флаг, чтобы немедленно отправить данные
    eui.StateDirty();
}
```
1.  `CrewManifestSystem` создает экземпляр серверного `CrewManifestEui`.
2.  Объект передается в `EuiManager`, который является ядром системы на сервере.
3.  `EuiManager` отправляет сетевое сообщение клиенту, приказывая ему создать и открыть EUI с соответствующим типом.

#### Шаг 2: Сервер готовит и отправляет состояние

Когда `EuiManager` решает отправить обновление (сразу после открытия или при изменении данных), он вызывает метод `GetNewState()` у серверного объекта EUI.

Файл: `Content.Server/CrewManifest/CrewManifestEui.cs`
```csharp
public override CrewManifestEuiState GetNewState()
{
    // Получаем актуальные данные из основной системы
    var (name, entries) = _crewManifest.GetCrewManifest(_station);

    // Создаем и возвращаем объект Состояния для отправки по сети
    return new CrewManifestEuiState(name, entries);
}
```
Объект `CrewManifestEuiState` (определен в `Content.Shared`) сериализуется и отправляется по сети клиенту.

#### Шаг 3: Клиент получает состояние и обновляет UI

На стороне клиента его `EuiManager` получает `CrewManifestEuiState` и передает его в соответствующий клиентский обработчик EUI.

Файл: `Content.Client/CrewManifest/CrewManifestEui.cs`
```csharp
public sealed class CrewManifestEui : BaseEui
{
    private readonly CrewManifestUi _window; // Ссылка на реальное окно

    // ... конструктор ...

    // Главный метод-обработчик входящих состояний
    public override void HandleState(EuiStateBase state)
    {
        // Проверяем, что пришел правильный тип состояния
        if (state is not CrewManifestEuiState cast)
            return;

        // Передаем данные в окно для отрисовки
        _window.Populate(cast.StationName, cast.Entries);
    }
}
```
1.  Клиентский EUI (`CrewManifestEui`) выступает в роли контроллера.
2.  В методе `HandleState` он "распаковывает" полученное состояние.
3.  Он вызывает метод `_window.Populate(...)`, который обновляет UI: очищает старые записи и отображает новый список экипажа.

#### Шаг 4: Обновление данных в реальном времени

Если данные на сервере меняются (например, прибывает новый член экипажа), происходит следующий цикл:
1.  `CrewManifestSystem` слушает игровые события и, при их наступлении, обновляет свой кэш данных.
2.  Затем она вызывает `eui.StateDirty()` для всех активных EUI, связанных с этими данными.
3.  Это заново запускает **Шаг 2**: `EuiManager` снова вызывает `GetNewState()`, и обновленное состояние отправляется всем подписанным клиентам.
4.  Клиенты проходят через **Шаг 3**, и игрок видит обновленный интерфейс.

### 10.3. Взаимодействие с пользователем (Клиент -> Сервер)

Хотя в `CrewManifestEui` нет сложного взаимодействия, общий паттерн таков:
1.  Пользователь нажимает кнопку в окне UI.
2.  Код окна вызывает метод у своего контроллера — клиентского EUI.
3.  Клиентский EUI вызывает `SendMessage(new MyMessage(...))`.
4.  `MyMessage` (определенное в `Content.Shared`) отправляется на сервер.
5.  Серверный EUI получает сообщение в методе `HandleMessage(EuiMessageBase msg)` и выполняет соответствующую логику.

Этот подход с четким разделением на серверную логику, общее состояние и клиентское отображение делает систему EUI мощным, предсказуемым и расширяемым инструментом для создания сложных интерфейсов.

## 11. Система таймеров шаттла: от сервера к клиенту

Таймеры, отображаемые на различных экранах в игре (например, таймер прибытия эвакуационного шаттла), являются результатом сложного взаимодействия нескольких систем. Они не являются простым UI элементом, а представляют собой визуализацию данных, передаваемых по сети.

### 11.1. Общая архитектура и поток данных

1.  **Инициация (Сервер)**: `RoundEndSystem` или `EmergencyShuttleSystem` инициируют обновление таймера. Например, при вызове шаттла в `RoundEndSystem.RequestRoundEnd` создается `NetworkPayload`.

2.  **Создание пакета (Сервер)**: Этот `NetworkPayload` представляет собой словарь, который заполняется данными о таймере:
    *   **Ключи**: Используются строковые константы из класса `ShuttleTimerMasks` (например, `ShuttleTimerMasks.DestTime`). Эти ключи фактически являются строками для локализации (`Loc.GetString(...)`).
    *   **Значения**: Временные метки (`TimeSpan`), `EntityUid` карт и шаттлов, флаги состояния (например, `Docked`).

3.  **Передача по сети устройств (Сервер)**: Готовый `NetworkPayload` отправляется через `DeviceNetworkSystem` в сеть устройств, к которой принадлежит шаттл. Это позволяет другим устройствам в той же сети (включая сами экраны) "слушать" эти обновления.

4.  **Обработка пакета на сервере (`ScreenSystem`)**: На сервере `Content.Server.Screens.Systems.ScreenSystem` подписывается на пакеты в сети устройств. Его задача — найти сущности с компонентом `TextScreenVisualsComponent` (т.е. игровые экраны) и обновить их внешний вид.

5.  **Обновление `Appearance` (Сервер)**: `ScreenSystem` не меняет спрайты напрямую. Вместо этого он использует `AppearanceSystem`, чтобы записать данные из пакета в `AppearanceComponent` сущности-экрана. Например: `_appearance.SetData(uid, TextScreenVisuals.TargetTime, targetTime)`.

6.  **Репликация на клиент**: Движок RobustToolbox автоматически отслеживает изменения в `AppearanceComponent` и реплицирует их всем клиентам, которые видят данную сущность.

7.  **Обработка на клиенте (`TextScreenSystem`)**:
    *   На клиенте `Content.Client.TextScreen.TextScreenSystem` является `VisualizerSystem`, который автоматически реагирует на изменения в `AppearanceComponent`.
    *   Его метод `OnAppearanceChange` получает обновленные данные.

8.  **Логика и отрисовка таймера (Клиент)**:
    *   `OnAppearanceChange` проверяет наличие данных `TextScreenVisuals.TargetTime`.
    *   Если время указано, система создает на сущности-экране `TextScreenTimerComponent` и сохраняет в нем целевое время.
    *   В основном цикле (`Update`) `TextScreenSystem` каждую карету проверяет все сущности с `TextScreenTimerComponent`.
    *   Она вычисляет оставшееся время (`timer.Target - _gameTiming.CurTime`).
    *   Оставшееся время форматируется в строку (например, "04:15") с помощью метода `TimeToString`.
    *   Наконец, система "рисует" эту строку на экране, заменяя каждый символ на соответствующий спрайт из `Effects/text.rsi`. Для этого используются методы `BuildTimerLayers` и `DrawLayers`, которые управляют слоями в `SpriteComponent`.

Таким образом, "таймер" — это не единый объект, а динамическая визуализация, управляемая асинхронной передачей данных от серверных игровых систем к клиентской системе рендеринга через промежуточные `DeviceNetworkSystem` и `AppearanceSystem`.

## 12. EUI Факса: Архитектура и жизненный цикл

Интерфейс факс-аппарата является более простым примером EUI, чем манифест экипажа, но следует той же архитектуре "сервер-авторитет". Сервер полностью контролирует состояние интерфейса (какие кнопки активны, какой список адресатов), а клиент лишь отображает это состояние и отправляет обратно сообщения о действиях пользователя.

### 12.1. Ключевые компоненты

1.  **Серверная система**: `Content.Server/Fax/FaxSystem.cs`
    *   **Роль**: Основная логика. Отвечает за открытие UI, формирование его состояния и обработку действий игрока.

2.  **Общее состояние и сообщения**: `Content.Shared/Fax/SharedFax.cs`
    *   `FaxUiState`: Класс, содержащий все данные для отображения в UI: имя устройства, список известных адресатов, текущий выбранный адресат и флаги доступности кнопок (`canSend`, `canCopy`).
    *   Сообщения от клиента к серверу (`FaxSendMessage`, `FaxCopyMessage`, `FaxRefreshMessage` и др.).

3.  **Клиентский обработчик EUI**: `Content.Client/Fax/UI/FaxBoundUi.cs`
    *   **Роль**: Посредник. Получает `FaxUiState` от сервера и передает его в окно для отрисовки.

4.  **Окно UI**: `Content.Client/Fax/UI/FaxWindow.xaml.cs`
    *   **Роль**: Отображение. Получает данные от `FaxBoundUi` и настраивает элементы управления (кнопки, списки). Также отвечает за отправку сообщений на сервер при нажатии кнопок.

### 12.2. Жизненный цикл UI факса

#### Шаг 1: Инициация и отправка состояния (Сервер)

В отличие от `CrewManifestEui`, у факса нет отдельного серверного класса `...Eui.cs`. Вся логика инкапсулирована внутри `FaxSystem.cs`.

Процесс начинается, когда игрок открывает интерфейс факса.

Файл: `Content.Server/Fax/FaxSystem.cs`
```csharp
// Вызывается при открытии UI
private void OnToggleInterface(EntityUid uid, FaxMachineComponent component, AfterActivatableUIOpenEvent args)
{
    UpdateUserInterface(uid, component);
}

// Главный метод для обновления UI
private void UpdateUserInterface(EntityUid uid, FaxMachineComponent? component = null)
{
    // 1. Проверяются различные условия (вставлена ли бумага, не в кулдауне ли отправка)
    // ...
    var isPaperInserted = component.PaperSlot.Item != null;
    var canSend = isPaperInserted && ...;
    var canCopy = isPaperInserted && ...;

    // 2. Собирается список известных факсов
    var peers = new Dictionary<string, FaxUiPeerInfo>();
    foreach (var (address, info) in component.KnownFaxes)
    {
        peers[address] = new FaxUiPeerInfo(info.Name);
    }

    // 3. Создается объект состояния
    var state = new FaxUiState(component.FaxName, peers, canSend, canCopy, isPaperInserted, component.DestinationFaxAddress);
    
    // 4. Состояние отправляется клиенту
    _userInterface.SetUiState(uid, FaxUiKey.Key, state);
}
```
`FaxSystem` напрямую создает `FaxUiState` и с помощью `UserInterfaceSystem` отправляет его клиенту. Этот же метод `UpdateUserInterface` вызывается при любом изменении состояния факса (вставили бумагу, пришел ответ на пинг), обеспечивая актуальность UI.

#### Шаг 3: Взаимодействие (Клиент -> Сервер)

Когда игрок нажимает кнопку, например, "Отправить", соответствующий обработчик в `FaxWindow.xaml.cs` создает и отправляет сообщение на сервер.

Файл: `Content.Client/Fax/UI/FaxWindow.xaml.cs`
```csharp
private void SendButtonPressed()
{
    SendMessage(new FaxSendMessage());
}
```
Это сообщение (`FaxSendMessage`) определено в `Content.Shared` и не несет в себе данных, оно просто служит сигналом к действию.

#### Шаг 4: Обработка сообщения (Сервер)

`FaxSystem` слушает это сообщение и выполняет соответствующее действие.

Файл: `Content.Server/Fax/FaxSystem.cs`
```csharp
private void OnSendButtonPressed(EntityUid uid, FaxMachineComponent component, FaxSendMessage args)
{
    // ... (проверка на моба в факсе)
    Send(uid, component, args);
}
```
Обработчик `OnSendButtonPressed` вызывает основной метод `Send`, который содержит всю логику отправки факса.

Этот цикл (сервер отправляет состояние -> клиент рисует UI -> клиент отправляет сообщение о действии -> сервер обрабатывает действие и отправляет новое состояние) является основой работы всех EUI в игре.
